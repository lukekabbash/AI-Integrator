# AI Integrator — QOL Microinteraction Catalog (200)

**Status:** Normative implementation backlog  
**Audience:** Product, design, desktop, frontend, adapter, protocol, accessibility, and QA teams  
**Research window:** 2026-07-10  
**Companion:** [Agent workspace UI/UX primitives](ui-ux-primitives.md), [Critical systems primitives](critical-systems-primitives.md), [Delivery and criticality matrix](delivery-criticality-matrix.md), [Native parity matrix](native-parity-matrix.md), [Product specification](product-spec.md)

This is the “little things” layer: two hundred small behaviors that make an agent workspace feel dependable rather than merely feature-complete. Each item specifies the user-facing behavior, its Codex and ACP relationship, its degraded path, and a testable acceptance check.

The list covers both meanings of “OS UI” relevant to this product:

- mature open-source interfaces whose actual code reveals edge cases that screenshots hide; and
- Windows/macOS desktop conventions that determine whether those interfaces feel native.

## 1. How protocol support maps to UI quality

Use these ownership labels consistently:

| Label | Meaning |
|---|---|
| **Client-owned** | AI Integrator must implement and persist the behavior; no agent protocol should own it |
| **Codex-native** | Current Codex app-server or desktop documentation exposes a direct primitive |
| **ACP-stable** | ACP v1 exposes a stable capability, method, notification, or content type |
| **ACP-draft** | An ACP RFD exists, but production UI must not require it yet |
| **Adapter-derived** | Integrator normalizes vendor events or combines protocol state with local state |

The central rule is: **capability support enables a good interface; it does not create one**. ACP and Codex can provide accurate state. Integrator still owns draft recovery, navigation, focus, scroll, grouping, language, platform behavior, and safety.

### 1.1 Current Codex primitives used here

Current app-server documentation exposes paginated thread history; read/resume/fork; names and goals; archive/unarchive/delete; runtime status; turn start/steer/interrupt; review; command and process sessions; model/effort catalogs; permission profiles; skills/hooks; MCP status/OAuth/elicitation; config requirements; filesystem operations; and structured notifications. `thread/archive` and `thread/delete` are different operations; `turn/interrupt` completes with an interrupted turn; user shell commands have a different sandbox boundary from turn commands. [Codex app-server API](https://learn.chatgpt.com/docs/app-server#api-overview)

The desktop app also documents full task search, separate Quick Chat, project/local-folder semantics, review scopes, inline comments, staged/unstaged/hunk actions, task-scoped terminals, deep links, and remappable shortcuts. [Projects and tasks](https://learn.chatgpt.com/docs/projects), [Commands](https://learn.chatgpt.com/docs/reference/commands), [Code review](https://learn.chatgpt.com/docs/code-review), [Integrated terminal](https://learn.chatgpt.com/docs/integrated-terminal)

### 1.2 Current ACP primitives used here

ACP v1 negotiates protocol version and capabilities at initialization. Stable primitives include session creation/loading/listing/deletion/resume/close, metadata updates, prompts and streamed updates, message ids, content blocks, tool kinds/status/content, permission options, client filesystem access, terminal lifecycle/output/truncation, full-list plan updates, session configuration categories, dynamic slash commands, usage updates, stop reasons, authentication, logout, and cancellation. [ACP overview](https://agentclientprotocol.com/protocol/v1/overview), [Initialization](https://agentclientprotocol.com/protocol/v1/initialization), [ACP updates](https://agentclientprotocol.com/updates)

Important limits:

- Omitted ACP capabilities mean unsupported; clients must not probe optimistically.
- Session config options supersede the older mode API.
- `session/delete` only guarantees removal from future session-list results; hard/soft deletion and active-session behavior are implementation-defined.
- Prompt cancellation is a notification followed later by a semantically meaningful cancelled result; it is not instant confirmation.
- Session fork and structured elicitation are still draft/preview RFDs, so side-chat and rich-question UI need a fallback. [Session fork draft](https://agentclientprotocol.com/rfds/session-fork), [Elicitation preview](https://agentclientprotocol.com/rfds/elicitation)

### 1.3 Source-level UI references

The open-source implementation pass particularly informed this list:

- Zed persists task drafts and logical scroll position, distinguishes selected/focused/hovered/archived/truncated row state, and has a real steer/queue state machine.
- Cline virtualizes transcripts, tracks whether the user left the bottom, keeps sticky request context, tests IME behavior, and distinguishes queued from steering prompts.
- OpenCode persists pane/file/review state, avoids first-frame width snapping, virtualizes large diffs, and uses typed question/permission/revert docks.
- GitHub Desktop makes resizers keyboard operable, clamped, double-click resettable, and announced through a live region.
- Goose remembers whether responsive sidebar collapse was automatic or user-selected.
- OpenCode suppresses delayed tooltips while their nested controls are expanded and gives toasts explicit actions, persistence, and dismissal semantics.
- OpenHands flips, shifts, and continuously repositions floating help while supporting both keyboard focus and pointer activation.
- Kilo Code replays missed prompts, permissions, questions, suggestions, and server state after reconnect instead of assuming the event stream was complete.
- GitHub Desktop restores focus after transient menus, separates retry actions by operation, and announces asynchronous state through dedicated live regions.

Pinned source snapshots are recorded in [Agent workspace UI/UX primitives](ui-ux-primitives.md#11-source-inspection-snapshot).

## 2. Entry, navigation, project identity, and history

### 001 — New task means “ready to type”

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Clicking New task immediately opens a draft and focuses the composer. It does not first open a runtime, permission, project, or template chooser.
- **Codex / ACP:** Codex has `thread/start`, but Integrator should delay it until send so an abandoned blank draft does not pollute native history. ACP `session/new` similarly should occur at send or when agent-derived config is needed.
- **Fallback:** If a runtime requires session creation to discover models/modes, create an ephemeral setup session and do not expose it as a task until meaningful input exists.
- **Acceptance:** From any shell region, New task produces a focused caret in under 100 ms and no native session appears in history until the draft becomes meaningful.

### 002 — Draft survives project selection

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** A user may type, attach files, then choose a local folder, recent project, or Git clone without losing text, selection, chips, or undo history.
- **Codex / ACP:** Codex thread/session cwd is fixed at start; ACP `session/new` and `session/load` take an absolute cwd. Therefore context selection should precede native session creation when possible.
- **Fallback:** If a native session was already created under the wrong cwd, preview a new session/handoff instead of silently mutating identity.
- **Acceptance:** A 5,000-character draft with selection and three attachments is byte-identical after folder picker cancel, project choice, failed clone, and successful clone.

### 003 — Project header opens an overview, not a surprise chat

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Selecting a project header opens roots, checkouts, dirty state, active tasks, guidance, skills, and a compact new-task entry. It never guesses which old task the user wants.
- **Codex / ACP:** Codex separates project organization from individual tasks. ACP sessions expose cwd and optional additional directories but define no project overview.
- **Fallback:** When a runtime cannot enumerate sessions, show Integrator-owned task history and label native history unavailable.
- **Acceptance:** Single-click project selection never starts/resumes a native session and always shows the exact roots that a new task would inherit.

### 004 — “Recent” is a view; search covers durable history

**Priority:** P0 · **Owner:** Client-owned plus native discovery

- **Behavior:** The rail may show recent tasks, but global search queries the complete Integrator index and native history where supported.
- **Codex / ACP:** Codex `thread/list` supports pagination and search terms. ACP `session/list` is capability-gated and cursor-paginated; cursors are opaque and must not be persisted.
- **Fallback:** Index locally retained transcripts and show `Native history not exposed` rather than returning an apparently complete empty result.
- **Acceptance:** A task outside all recent-item caps is findable by title, prompt phrase, branch, and project; exhausting ACP pages never blocks the UI thread.

### 005 — Archive, remove, and delete never share semantics

**Priority:** P0 · **Owner:** Client-owned safety

- **Behavior:** Archive hides/preserves; Remove detaches a project/root; Delete task removes Integrator history; Delete native session invokes vendor deletion; Delete worktree/branch affects Git/files. Each is named separately.
- **Codex / ACP:** Codex has distinct archive, unarchive, and permanent delete methods. ACP stable v1 has `session/delete` but no standard archive and does not guarantee hard deletion.
- **Fallback:** Implement Integrator archive locally and label vendor cleanup separately. Do not map local Archive to ACP Delete.
- **Acceptance:** Every destructive confirmation lists the exact Integrator record, native session, worktree, branch, and filesystem effects; archive is reversible.

### 006 — Back and forward follow semantic navigation

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Back returns from file/diff/settings/project overview to the prior semantic location, including selected task, event, file, and line—not merely the prior route string.
- **Codex / ACP:** Codex desktop documents back/forward shortcuts and deep links. Neither app-server nor ACP owns view history.
- **Fallback:** If the exact event/file vanished, return to the owning task and announce the missing anchor.
- **Acceptance:** Open task → diff line → file → settings; four Back actions reverse those states with focus and scroll position restored.

### 007 — Task switch restores focus and reading anchor

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Every task remembers transcript density, semantic top anchor plus offset, last focused region, composer selection, open work pane, selected file/diff, and unread boundary.
- **Codex / ACP:** Native session read/load supplies content, not UI state. Zed/OpenCode source implementations demonstrate that draft/scroll/pane state must be stored by the client.
- **Fallback:** If the anchor event is missing after compaction or replay, restore the nearest earlier turn and show `Original position changed`.
- **Acceptance:** Switching among ten streaming tasks 100 times never moves a task from Reading to Following and never loses a draft selection.

### 008 — Open in new window does not duplicate ownership

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Middle-click/context menu can open a task in another window. Only one window owns composer input; other windows are live read-only until they explicitly Take control.
- **Codex / ACP:** Multiple app-server subscribers and ACP clients may observe sessions, but concurrent prompt ownership and conflict semantics vary. Integrator arbitrates locally.
- **Fallback:** For runtimes that cannot safely support multiple observers, secondary windows show a cached view with Refresh/Take control.
- **Acceptance:** Two windows cannot submit conflicting prompts from the same draft; taking control transfers selection/draft without duplication.

### 009 — Checkout identity is always one glance away

**Priority:** P0 · **Owner:** Client-owned plus adapter metadata

- **Behavior:** Task header/composer can reveal project alias, actual checkout path, branch/worktree, dirty state, and environment. Similar clones never collapse into one anonymous project row.
- **Codex / ACP:** Codex threads carry cwd and Git metadata; ACP session info carries immutable absolute cwd and optional additional directories. Neither remote URL alone is sufficient identity.
- **Fallback:** When Git metadata is unavailable, show canonical local path and `Git state unavailable`.
- **Acceptance:** Three clones of the same remote on different branches are visually and searchably distinct without opening a details dialog.

### 010 — Attention is a reference, not a duplicate task

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Needs attention is a derived projection. Selecting an approval/failure/unread result opens the original task/event and does not create a second row with independent read state.
- **Codex / ACP:** Codex approval requests include thread/turn/item identity; ACP permission requests include session and tool-call identity. Use those keys for deduplication.
- **Fallback:** If an adapter lacks stable request ids, synthesize a scoped id and label correlation confidence in diagnostics.
- **Acceptance:** The same child approval surfaced at child, parent, and global levels resolves everywhere from one decision and produces one audit record.

## 3. Composer, text input, context, and queue

### 011 — Draft belongs to the task, not the DOM node

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Persist text, selection, undo-safe attachment model, intended delivery type, and expanded-editor state per task after 250 ms idle and immediately on navigation/blur/quit.
- **Codex / ACP:** Neither protocol is draft storage. Do not send draft text through native session methods until submission.
- **Fallback:** If attachment bytes cannot be persisted, retain metadata with `Reattach required` instead of silently dropping the chip.
- **Acceptance:** Crash the renderer mid-word; restart restores all but at most the last 250 ms of typing, without creating a native user message.

### 012 — Enter is IME-safe

**Priority:** P0 · **Owner:** Client-owned accessibility

- **Behavior:** Enter submits only when composition is inactive. Shift+Enter inserts newline; user remapping is reflected in tooltip and placeholder.
- **Codex / ACP:** Prompt methods accept completed content only and cannot repair an accidental partial composition.
- **Fallback:** If the webview/native text stack reports uncertain composition, prefer newline/no submit.
- **Acceptance:** Chinese, Japanese, Korean, dead-key, emoji, and dictation tests never submit during composition and preserve undo history.

### 013 — Paste adapts to size and type without freezing

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Small text pastes inline; large text becomes a previewable text attachment; images become thumbnails; file paths offer mention conversion; binary/unsupported data explains rejection.
- **Codex / ACP:** ACP prompts support text/resource links and capability-gated image, audio, and embedded resource blocks. Codex turn input supports structured content. Negotiate before conversion.
- **Fallback:** Save large local paste as an Integrator artifact and send a resource link/path or summarized text according to runtime support.
- **Acceptance:** Pasting 5 MB text or a 20 MB image keeps typing responsive and previews exactly what the runtime will receive.

### 014 — Context chips say snapshot versus live reference

**Priority:** P0 · **Owner:** Client-owned provenance

- **Behavior:** Each chip states `Captured selection`, `Embedded file`, `Live path`, `Indexed folder`, or `External source`, plus stale/missing state.
- **Codex / ACP:** ACP distinguishes embedded `resource` from `resource_link`; embedded context is capability-gated. Codex filesystem/mentions may reference live paths.
- **Fallback:** If the runtime cannot embed content, show the path/reference downgrade before send.
- **Acceptance:** Editing a captured file after attachment visibly marks the chip stale and offers Send captured, Refresh, or Remove.

### 015 — Dragging context previews the exact drop result

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Dragging a file, folder, diff hunk, screenshot, source, or task over the composer shows the resulting chip type and scope before drop.
- **Codex / ACP:** After drop, translate to Codex input items or ACP content blocks/cwd roots only if supported.
- **Fallback:** Unsupported folders become a validated path reference rather than recursively reading contents.
- **Acceptance:** The overlay says `Attach 3 files`, `Reference folder (not full contents)`, or `Attach 14-line diff selection`; drop never surprises with broader scope.

### 016 — Missing attachments remain visible and repairable

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Deleted, moved, permission-denied, offline, or changed attachments remain as error/stale chips with Locate, Refresh, Use snapshot, or Remove.
- **Codex / ACP:** Validate before constructing native prompt items. ACP resource links require a URI/name; embedded resources should carry the captured content.
- **Fallback:** A previously captured snapshot can still send when policy permits; otherwise block submission with one actionable message.
- **Acceptance:** No attachment disappears silently between draft creation and send, including after restart or checkout switch.

### 017 — Composer growth stops before it hides the work

**Priority:** P0 · **Owner:** Client-owned layout

- **Behavior:** Grow to six visual lines, then scroll internally. A shortcut opens a full draft editor without changing the task or losing selection.
- **Codex / ACP:** Protocol-independent. Open-source agents repeatedly cap queues/docks and separate full editors for this reason.
- **Fallback:** At narrow widths the expanded editor becomes the primary routed view with Back to task.
- **Acceptance:** A 20,000-character draft never covers the current activity or last response; compact/expanded transitions preserve caret pixel position where possible.

### 018 — Steer now and Send next are explicit

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** While a run is active, submit offers Steer now or Send next. Queue rows can be edited, reordered where safe, converted, sent now, or cancelled.
- **Codex / ACP:** Codex exposes `turn/steer`; its CLI also queues slash commands for the next turn. ACP v1 has no standard steer/queue primitive, so Send next is client-owned and Steer is adapter capability.
- **Fallback:** For ACP-only agents, disable Steer and queue locally; dispatch the next `session/prompt` only after the prior prompt response settles.
- **Acceptance:** A queued prompt is never displayed as already sent, and stopping a run pauses rather than drains the local queue.

### 019 — Chip conversion and removal are undoable

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Converting pasted paths to mentions, bundling large paste, removing context, or clearing the composer participates in the draft undo stack.
- **Codex / ACP:** Only the final committed prompt maps to protocol content. Keep intermediate representation local.
- **Fallback:** A brief Undo toast restores serialized chip state if native text undo cannot represent the operation.
- **Acceptance:** Ctrl/Cmd+Z restores the exact chip, insertion point, label, snapshot hash, and stale state without rereading the file.

### 020 — Crash recovery is quiet and explicit

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Restored drafts show one subtle `Draft recovered after restart` indicator with timestamp and Dismiss; no modal and no repeated toast.
- **Codex / ACP:** Reconcile native session/run separately; restored local draft must never be mistaken for a native user turn.
- **Fallback:** If recovery data is corrupt, preserve it as a downloadable/redacted text artifact and start an empty draft.
- **Acceptance:** Recovery appears once, is screen-reader announced once, and never auto-submits even if the native task completed while the app was closed.

## 4. Runtime, model, mode, effort, and permissions

### 021 — One sentence exposes the effective launch context

**Priority:** P0 · **Owner:** Client-owned synthesis

- **Behavior:** Above an empty composer, say `Working in Lotmind AI on worktree mobile-intake · Auto will use Codex · project-write access`. Every variable phrase opens its control.
- **Codex / ACP:** Compose from Codex cwd/Git metadata, `model/list`, permission profiles, environment and project policy; or ACP session cwd/config options plus Integrator policy.
- **Fallback:** Unknown values say `Runtime chosen on send` or `Permission details unavailable`, never a guessed default.
- **Acceptance:** A user can accurately name checkout, runtime/profile, isolation, and effective permission without opening Settings.

### 022 — Agent-advertised config lands in predictable places

**Priority:** P0 · **Owner:** Client-owned rendering of native config

- **Behavior:** Model and model configuration share one popover; reasoning/thought level sits beside model; mode/permission sits in its own control; unknown options go under Runtime options in advertised order.
- **Codex / ACP:** Codex has model plus effort and permission/collaboration selectors. ACP config categories explicitly define `model`, `model_config`, `thought_level`, and `mode`, with array order as priority.
- **Fallback:** Missing/unknown ACP categories render in a generic labeled control and never become correctness dependencies.
- **Acceptance:** Two runtimes advertising the same semantic categories appear in the same places while retaining their native names/descriptions.

### 023 — Selector width does not jump when values change

**Priority:** P1 · **Owner:** Client-owned visual stability

- **Behavior:** Model/mode/permission chips reserve a bounded width; label changes crossfade or truncate without shifting Send, voice, or adjacent controls.
- **Codex / ACP:** Models and config can change after rate limits, mode transitions, or dependent-option updates.
- **Fallback:** On narrow windows, show stable glyph + short label and put the full value in tooltip/popover.
- **Acceptance:** Switching among the shortest and longest fixture labels moves no neighboring control by more than one device pixel.

### 024 — Auto always has a “Why this profile?” answer

**Priority:** P0 · **Owner:** Client-owned routing transparency

- **Behavior:** Auto details list selected runtime/model/effort, top decision factors, freshness, fallback, and rejected options with short reasons.
- **Codex / ACP:** Native catalogs provide availability/capabilities, not Integrator's cross-runtime routing decision. The explanation is adapter/client-derived.
- **Fallback:** If usage or capability data is stale, state that directly and exclude it from decisive language.
- **Acceptance:** Every automatic choice produces a deterministic, exportable decision record without exposing hidden model reasoning.

### 025 — Agent-driven config changes are visible, not spooky

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** If a runtime changes model, mode, or effort, update the control in place and add one compact event: `Model changed to X · rate-limit fallback` when a reason is known.
- **Codex / ACP:** ACP `config_option_update` carries a complete current config list and may reflect fallback/model-dependent options. Codex turn/thread settings can similarly be reconciled from native events/state.
- **Fallback:** Without a stated reason, say `Runtime changed model` and never invent why.
- **Acceptance:** The control, transcript event, audit record, and next-turn profile agree after an agent-side change.

### 026 — Permission choices keep native meaning

**Priority:** P0 · **Owner:** Adapter-derived safety

- **Behavior:** Display the runtime's offered decisions—Allow once, Always allow, Reject, Always reject—while showing Integrator policy if it narrows them.
- **Codex / ACP:** ACP permission options carry stable kinds `allow_once`, `allow_always`, `reject_once`, and `reject_always`. Codex approval requests expose available decisions and later `serverRequest/resolved`.
- **Fallback:** If only yes/no is available, show Allow once/Reject and do not fabricate persistent permission rules.
- **Acceptance:** Selecting a persistent option produces a visible rule scope and never silently exceeds parent/project policy.

### 027 — Approval cards name what, where, why, and how long

**Priority:** P0 · **Owner:** Client-owned rendering

- **Behavior:** Every approval names tool/action, command or destination, cwd/path, requesting run, reason, policy source, and whether the choice is once or persistent.
- **Codex / ACP:** Codex distinguishes command, managed network, file-change, and permission requests and can include host/protocol/port or absolute additional paths. ACP attaches the request to a tool call and offers decision kinds.
- **Fallback:** Missing fields render `Not provided by runtime`; raw details remain redacted and inspectable.
- **Acceptance:** Network approval never masquerades as a generic shell approval, and two different ports remain separately understandable.

### 028 — Mid-run mode changes distinguish current from next effect

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** A mode/permission/model change while generating says `Applies now` only if the runtime confirms it; otherwise `Applies to the next operation/turn`.
- **Codex / ACP:** ACP allows setting config options or modes while an agent is generating and may send an update back. Codex supports turn steering and runtime configuration but individual effects depend on the native primitive.
- **Fallback:** Default to next-operation semantics and offer Stop then restart if immediate enforcement is required.
- **Acceptance:** The audit record includes requested time, acknowledged time, returned native state, and first operation governed by the new value.

### 029 — Unsupported capabilities disappear cleanly but remain explainable

**Priority:** P0 · **Owner:** Capability-driven client

- **Behavior:** Do not show a dead image upload, terminal, resume, delete, boolean option, or MCP transport control. Search/advanced details may show `Unavailable` with the negotiated reason.
- **Codex / ACP:** ACP requires omitted capabilities to be treated as unsupported. Codex app-server has explicit experimental capability gates and under-development methods that should not enter production clients.
- **Fallback:** Offer a faithful alternative such as path text, external terminal, new session with handoff, or local-only archive.
- **Acceptance:** The UI issues zero unsupported protocol calls in capability-matrix tests and every hidden P0 feature has a discoverable explanation.

### 030 — Dependent config options refresh atomically

**Priority:** P0 · **Owner:** Client-owned state reconciliation

- **Behavior:** After changing model/mode, replace the complete returned option set in one state transaction so reasoning choices, defaults, and available values never show an impossible combination.
- **Codex / ACP:** ACP `session/set_config_option` and `config_option_update` return the complete configuration state specifically to support dependencies. Codex `model/list` includes per-model effort/input capability data.
- **Fallback:** While refreshing, keep the last valid selection visible but disabled with `Updating options…`; do not clear it to blank.
- **Acceptance:** Fixture where a model change removes the selected thought level never renders that invalid pair, even for one animation frame.

## 5. Streaming, transcript, grouping, and scroll

### 031 — Chunks stream; messages do not repeatedly enter

**Priority:** P0 · **Owner:** Client-owned rendering

- **Behavior:** A message gets one entrance at most. Further text chunks append without per-token fades, typewriter animation, cursor theater, or repeated screen-reader announcements.
- **Codex / ACP:** Both Codex item deltas and ACP `agent_message_chunk` are streaming transport units, not separate visual messages.
- **Fallback:** Batch unknown high-frequency events into 30 Hz visual updates while preserving raw order in durable storage.
- **Acceptance:** A 20,000-chunk fixture creates one message node/animation and keeps composer input within latency budget.

### 032 — Auto-follow stops when the user starts reading

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Follow new output only while at the end. Upward scroll, selection, find, comment editing, or opening an earlier disclosure enters Reading state.
- **Codex / ACP:** Protocols continue streaming independently; the client must decouple ingestion from viewport movement. Cline and Zed source implementations explicitly track this.
- **Fallback:** If exact scroll metrics are unreliable during virtualization, err toward preserving the user's position.
- **Acceptance:** Selecting text 500 rows above the bottom remains pixel-stable while 1,000 events arrive.

### 033 — “New events” goes to the first unread, not blindly to bottom

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Show `↓ 12 new events`. First activation goes to the unread divider; a second activation or Follow button resumes end-following.
- **Codex / ACP:** Unread is local view state; native events supply stable item/session identity and timestamps.
- **Fallback:** If an adapter lacks item ids, use durable normalized event sequence numbers.
- **Acceptance:** After 12 events and completion, the user sees all unseen content in order and the unread count clears only after it is viewed.

### 034 — The active request stays recoverable

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Once the current user request scrolls away, show a one-line sticky summary that expands to the exact request and attachments.
- **Codex / ACP:** Derive from the current turn/session prompt; do not ask the runtime to repeat or summarize it.
- **Fallback:** Long/complex requests use a locally generated deterministic truncation plus `Show full request`, not a model-generated paraphrase.
- **Acceptance:** During a two-hour event-heavy run, the full assignment is accessible in one action without changing context or scroll anchor.

### 035 — Message IDs define grouping; arrival timing does not

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Chunks with one message id update one message. A new id creates a new semantic message even if both arrive in the same frame.
- **Codex / ACP:** ACP message ids are opaque and define chunk membership; Codex item ids/turn ids provide equivalent grouping.
- **Fallback:** If no id exists, group by normalized event lifecycle with a documented heuristic and confidence marker in diagnostics.
- **Acceptance:** Interleaved chunks for two child/tool contexts never merge into one bubble or reorder after replay.

### 036 — Tool cards patch in place through their lifecycle

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Pending → waiting approval → in progress → completed/failed/declined/cancelled updates one stable card. Content, locations, diffs, and terminal references append without duplicating the call.
- **Codex / ACP:** Codex item started/updated/completed and ACP `tool_call`/`tool_call_update` with `toolCallId` are patch-oriented; ACP updates may omit unchanged fields.
- **Fallback:** Normalize runtimes with only start/end text into one synthesized lifecycle and retain raw lines in diagnostics.
- **Acceptance:** One logical tool call produces one focusable row, one audit id, and one final status across live stream and replay.

### 037 — Stop progresses through request, settling, and confirmation

**Priority:** P0 · **Owner:** Adapter-derived safety

- **Behavior:** UI states are Stop requested → Cancelling tools → Interrupted/Cancelled, with elapsed time and force/diagnostic options only when available.
- **Codex / ACP:** Codex `turn/interrupt` returns success and ends the turn interrupted. ACP `session/cancel` is a notification; the agent may still send updates before the original prompt returns `cancelled`. Generic `$/cancel_request` is optional.
- **Fallback:** If control acknowledgement is lost, show `Cancellation unconfirmed` and preserve process controls separately.
- **Acceptance:** The UI accepts valid late tool updates after cancel, cancels outstanding approvals, and never labels the turn stopped before final native state.

### 038 — Stop reasons become distinct outcomes

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Ended normally, token limit, turn-request limit, refusal, user cancelled, failed, and disconnected have different copy/actions.
- **Codex / ACP:** ACP prompt responses define `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, and `cancelled`; Codex turns/items carry runtime statuses and error/interruption outcomes.
- **Fallback:** Unknown vendor termination is `Ended — reason unavailable`, not success.
- **Acceptance:** Completion ledger cannot treat token-limit/refusal/cancelled/unknown as verified completion.

### 039 — Collapsed activity summaries disclose bad news

**Priority:** P0 · **Owner:** Client-owned projection

- **Behavior:** A collapsed group states type, count, elapsed, completion, failure/warning count, and unresolved attention. It never collapses away an approval or error.
- **Codex / ACP:** Derive from structured item/tool kinds and final statuses. ACP kinds include read/edit/delete/move/search/execute/think/fetch/other.
- **Fallback:** Unknown items appear in the count as `runtime events`; failures remain separately visible.
- **Acceptance:** `Ran 8 commands · 2 failed · 41s` remains truthful in Summary, Normal, Verbose, and after replay.

### 040 — Session replay does not look like fresh activity

**Priority:** P0 · **Owner:** Adapter-derived restoration

- **Behavior:** While loading/resuming, render historical events without entrance animation, unread increments, notifications, sound, or approval prompts already resolved.
- **Codex / ACP:** Codex `thread/read` can return history without resuming; ACP `session/load` replays the entire conversation through `session/update` notifications before continuing.
- **Fallback:** Tag the adapter connection as replay mode until load completes or a clear live boundary is observed.
- **Acceptance:** Loading a 10,000-event session generates zero completion notifications and preserves historical timestamps/statuses exactly.

## 6. Tool calls, files, locations, terminals, and process output

### 041 — Tool icon comes from semantic kind, not vendor branding

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Read, edit, delete, move, search, execute, plan/think, fetch, and other use stable action glyphs across runtimes; the runtime logo appears only in metadata.
- **Codex / ACP:** ACP `ToolKind` exists partly so clients can choose icons and progress treatment. Codex structured items can be normalized to the same taxonomy.
- **Fallback:** Unknown kinds use a neutral tool glyph and the runtime-provided human title.
- **Acceptance:** A file delete never uses the same visual as a read, and provider switching does not retrain action recognition.

### 042 — Permission stays attached to the requesting tool

**Priority:** P0 · **Owner:** Client-owned rendering

- **Behavior:** The approval dock and attention item link to the exact pending tool card; answering scrolls/highlights that card and updates it in place.
- **Codex / ACP:** Codex carries thread/turn/item ids; ACP permission requests include session plus tool-call id/update.
- **Fallback:** For PTY prompts, capture a bounded terminal excerpt and process id as the request anchor.
- **Acceptance:** With five simultaneous tools, the user can identify which command/path each approval unlocks and no response applies to the wrong call.

### 043 — Follow-along highlights; it does not steal the pane

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Agent file locations quietly update a `Working in…` status and highlight the file tree. Auto-opening files is opt-in and pauses when the user is reading/editing another file.
- **Codex / ACP:** ACP tool calls can report absolute file locations and 1-based line numbers; Codex file/tool items expose equivalent paths.
- **Fallback:** Without structured locations, parse only trusted adapter events—not arbitrary prose—to avoid false navigation.
- **Acceptance:** A user editing file A is never switched to file B by background activity; Follow agent resumes only on explicit action.

### 044 — Every path opens at the most specific known location

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Click opens file/preview at known line/range; modifier-click opens preferred editor; context menu offers Attach, Open in Integrator, Open in editor, Reveal, Copy relative, Copy absolute.
- **Codex / ACP:** ACP requires absolute paths and 1-based lines; Codex review/file links support editor navigation and configured preferred editor.
- **Fallback:** Missing path opens recovery with original checkout, Search moved file, and Copy original path.
- **Acceptance:** Path navigation is exact for spaces, Unicode, long Windows paths, UNC, symlinks, and WSL mappings.

### 045 — Agent reads can include unsaved editor state

**Priority:** P1 · **Owner:** Client capability

- **Behavior:** When an editor bridge owns a dirty buffer, reads go through the client capability and the UI labels `Includes unsaved changes`.
- **Codex / ACP:** ACP `fs/read_text_file` explicitly permits client-provided unsaved editor contents; capability must be negotiated. Codex IDE/app bridges can attach open selections/files through their native context path.
- **Fallback:** Without the capability, send a captured selection/resource or require Save; never imply disk content includes unsaved edits.
- **Acceptance:** A fixture with divergent disk/buffer contents shows the correct bytes and provenance to the agent and user.

### 046 — User edits and agent edits retain provenance

**Priority:** P0 · **Owner:** Client-owned evidence

- **Behavior:** Integrator spot edits, external editor changes, agent writes, Git operations, and conflict resolutions record distinct origins.
- **Codex / ACP:** ACP filesystem writes let the client observe agent-requested modifications; Codex item/filesystem events provide native provenance. Git diffs alone cannot establish authorship.
- **Fallback:** Mark overlapping or externally discovered changes `Origin mixed/unknown` rather than attributing them to the last agent.
- **Acceptance:** Last-turn review warns when its files include manual or other-agent changes and never claims exclusive authorship without evidence.

### 047 — Output truncation is impossible to miss

**Priority:** P0 · **Owner:** Client-owned rendering

- **Behavior:** Truncated command output shows `Earlier output truncated · retained last 1.0 MB`, with Open full log when a spill file exists.
- **Codex / ACP:** ACP terminal output returns a required `truncated` flag and respects an output-byte limit; Codex command/process streams can be locally bounded with durable spill.
- **Fallback:** If the runtime truncates without a count, say `Output truncated by runtime` and do not estimate retained bytes.
- **Acceptance:** Search/copy never pretends omitted content was searched, and truncation remains visible after the process exits and session reloads.

### 048 — Released/background terminal output remains inspectable

**Priority:** P1 · **Owner:** Client-owned terminal lifecycle

- **Behavior:** Releasing an agent terminal frees live process resources but preserves its final output, exit status, command, cwd, and tool-card link.
- **Codex / ACP:** ACP says embedded terminal output continues to display even after `terminal/release`; Codex exposes background terminal listing/termination and command/process output events.
- **Fallback:** Snapshot bounded output into an artifact before losing a PTY-only session.
- **Acceptance:** Closing/releasing a completed terminal never blanks a verification card or breaks a transcript link.

### 049 — Kill, release, close tab, and stop task are different

**Priority:** P0 · **Owner:** Client-owned semantics

- **Behavior:** Kill terminates process; Release gives up terminal resource; Close tab hides UI and asks about a running process; Stop task cancels the agent turn and handles its tools.
- **Codex / ACP:** ACP `terminal/kill`, `terminal/release`, and prompt cancellation are separate. Codex command terminate, background terminal terminate/clean, and turn interrupt are separate.
- **Fallback:** Hide unavailable actions rather than mapping them to the nearest dangerous primitive.
- **Acceptance:** Every command is unit-tested against the intended process/session call and confirmation copy states whether work keeps running.

### 050 — Command/environment display is redacted before persistence

**Priority:** P0 · **Owner:** Client-owned security

- **Behavior:** Show command/cwd and environment variable names, but redact secret values in approval, transcript, clipboard defaults, logs, exports, and crash reports.
- **Codex / ACP:** Codex approvals can contain commands/cwd and additional permissions. ACP terminal creation can include environment name/value pairs. Wire availability is not display authorization.
- **Fallback:** If a command cannot be safely tokenized, show a safe summary plus `Sensitive command hidden`; allow an explicit guarded reveal only when policy permits.
- **Acceptance:** Seeded secrets never appear in persisted database, search index, accessibility tree, telemetry, copied diagnostics, or screenshots.

## 7. Diff, review, comments, staging, and Git safety

### 051 — Review scope is always written as two endpoints

**Priority:** P0 · **Owner:** Client-owned Git UX

- **Behavior:** Header says `Unstaged ↔ index`, `Staged ↔ HEAD`, `feature ↔ origin/main`, `Last turn: run 4`, or `Candidate A ↔ Candidate B`.
- **Codex / ACP:** Codex documents Unstaged, Staged, Commit, Branch, and Last turn. ACP diff content supplies file before/after, not repository review scopes.
- **Fallback:** ACP-only agents open an Integrator-computed Git review; non-Git tasks show artifact/file comparison instead.
- **Acceptance:** No review surface uses a context-free label like `Changes` when more than one base is possible.

### 052 — Last-turn review carries an attribution caveat

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Last turn shows native/observed edits for that run plus `Working tree may include overlapping manual or other-agent edits` when provenance overlaps.
- **Codex / ACP:** Codex offers Last turn while its general review pane reflects repository state from all sources. ACP has tool-call ids/diffs but no universal Git provenance ledger.
- **Fallback:** If edit attribution is incomplete, fall back to task-start or working-tree scope and label the reason.
- **Acceptance:** Manual edits made during a run are never silently included under a heading that implies the agent alone produced them.

### 053 — The same file may correctly appear in Staged and Unstaged

**Priority:** P0 · **Owner:** Client-owned Git education

- **Behavior:** When a file has both index and working-tree changes, show it in both scopes with a quiet explanation, not dedupe it away.
- **Codex / ACP:** Codex documentation explicitly calls this normal Git behavior. ACP does not model the index.
- **Fallback:** If Git status cannot be read, disable staging actions and keep raw diff review.
- **Acceptance:** Partial-stage fixture renders both variants, with stage/unstage/revert operating on the correct side.

### 054 — Inline comment affordance is not hover-only

**Priority:** P0 · **Owner:** Client-owned accessibility

- **Behavior:** Pointer hover may reveal `+`, but keyboard line navigation exposes Add comment through a command/key and screen readers announce commentable ranges.
- **Codex / ACP:** Codex review supports line-specific feedback. ACP v1 diff content does not standardize review comments; Integrator owns draft comments and projects them into the next prompt.
- **Fallback:** Attach file/range/comment as structured local context or faithful text when the runtime lacks comment input.
- **Acceptance:** A keyboard-only user adds, edits, sends, and returns to a line comment without using a pointer.

### 055 — Stale comments stay visible and ask to re-anchor

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Bind draft comments to path, side, content hash, and line/range. On diff refresh, preserve exact matches; otherwise mark stale and offer nearest candidates.
- **Codex / ACP:** Neither protocol solves comment re-anchoring. Use native ids/hashes where exposed and Integrator content matching otherwise.
- **Fallback:** Send a stale comment only with a preview containing the captured code excerpt and current mismatch.
- **Acceptance:** Refreshing after line insertions does not silently move a comment to unrelated code.

### 056 — Diff-to-file navigation has a return stack

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Open exact working-tree line from diff, then Back returns to the same hunk/comment and scroll offset.
- **Codex / ACP:** Codex documents file/editor navigation; ACP diff paths are absolute and line-aware tool locations may supplement mapping.
- **Fallback:** If mapping is stale, open nearest line with `Original line unavailable` and retain the diff anchor.
- **Acceptance:** Navigation survives file edits, pane resize, and external editor round trip without losing the source hunk.

### 057 — Unsupported, deleted, binary, and huge diffs explain themselves

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Show metadata and an action for binary/too-large/generated/partial/deleted files; never an empty review pane.
- **Codex / ACP:** ACP v1 diff content supports old text nullable for new files and requires new text; deleted-file representation remains a draft RFD. Codex review/Git can cover richer file states.
- **Fallback:** Compute Git/binary metadata locally or offer Open externally; label adapter/protocol limitation.
- **Acceptance:** Fixtures for deletion, rename, image, PDF, submodule, lockfile, 100 MB file, and truncated patch each produce an explicit state.

### 058 — Bulk Git actions preview scope and retain safe undo

**Priority:** P0 · **Owner:** Client-owned Git safety

- **Behavior:** Stage all, Unstage all, Revert file/hunk, and Discard state file/hunk counts and base. Reversible local operations expose Undo; irreversible ones confirm.
- **Codex / ACP:** Codex review supports entire diff, file, and hunk actions. ACP does not standardize Git index operations.
- **Fallback:** Use locally supervised Git commands under Integrator policy; never ask a generic ACP agent to simulate a UI action invisibly.
- **Acceptance:** Bulk action tests verify exact index/working-tree result with untracked, partially staged, renamed, and conflicted files.

### 059 — Review warns when the working tree changes underneath it

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Filesystem/Git watchers mark a review stale and offer Refresh while preserving selection/comments; destructive actions require current data.
- **Codex / ACP:** Codex filesystem/Git state can change from user, agent, or tools. ACP client filesystem methods allow tracking writes but do not catch all external changes.
- **Fallback:** Re-read Git status immediately before stage/revert and abort on mismatch.
- **Acceptance:** External edit between review render and Revert cannot discard unseen content.

### 060 — Current versus detached review is remembered and visible

**Priority:** P1 · **Owner:** Client-owned preference

- **Behavior:** Reviewing in the current task preserves context; detached review creates a linked review task. The setting is remembered, and the launch affordance says which will happen.
- **Codex / ACP:** Codex officially supports current-task or Detached review. ACP has no review-task primitive; detached review is a new Integrator task/session with an attached diff/handoff.
- **Fallback:** If a runtime cannot create/resume a suitable review session, run review locally/current and label it.
- **Acceptance:** Detached review never writes to the parent task's model-visible history, and its findings link back to the exact scope.

## 8. Plans, goals, child agents, side questions, and comparison

### 061 — Plan replacement preserves visual continuity without inventing ids

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** When a runtime sends a complete revised plan, replace plan truth atomically but visually match unchanged rows by normalized content for stable focus/scroll. Mark changed text/status briefly.
- **Codex / ACP:** Codex exposes goals and plan items/events. ACP plan updates always contain the complete list and require clients to replace the current plan; entries have content, priority, and pending/in-progress/completed status but no stable id.
- **Fallback:** If matching is ambiguous, replace without row motion and move focus to the plan heading.
- **Acceptance:** Reordering or editing two of ten ACP plan entries never falsely transfers completion state or drops keyboard focus into the wrong row.

### 062 — Progress counts only real, stable work units

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Show `3 of 7 steps` only when the current plan provides seven meaningful entries. Never convert tool count, elapsed time, or token flow into a fake percentage.
- **Codex / ACP:** ACP provides discrete plan entry statuses; Codex goal/plan state may provide discrete steps. Neither justifies arbitrary percent complete.
- **Fallback:** Show current phase and completed/pending counts or indeterminate status.
- **Acceptance:** Plan revisions that add/remove steps recompute counts with an `Updated plan` note rather than animating backward percentage.

### 063 — Agent plan and user-approved plan are distinct layers

**Priority:** P1 · **Owner:** Client-owned task contract

- **Behavior:** The agent-reported plan is live execution state. A user-edited plan is a local accepted document sent as guidance on the next turn; editing never rewrites historical native events.
- **Codex / ACP:** ACP plans are agent-to-client updates, not editable protocol documents. Codex task goals are settable, while plan messages/events remain native history.
- **Fallback:** Export/edit Markdown and attach the revision as context.
- **Acceptance:** The UI can show `Agent plan v4` and `Accepted plan v2` with a diff and no ambiguity about which drives displayed runtime progress.

### 064 — Child cards show one useful live sentence

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Each child card shows role, runtime/model, scope, checkout, elapsed/status, and latest observable activity such as `Running security tests`, not raw last token.
- **Codex / ACP:** Codex has spawned thread relationships and thread status/filtering. ACP v1 has concurrent sessions but no stable parent/child semantics; adapters/Integrator provide lineage.
- **Fallback:** Use explicit delegated-task metadata and session id; label lineage `Integrator-managed`.
- **Acceptance:** A supervision grid of 16 agents is understandable without opening any transcript and never displays private/simulated thinking.

### 065 — Child approvals promote to parent/global attention once

**Priority:** P0 · **Owner:** Client-owned attention routing

- **Behavior:** A blocking child approval appears on child, parent, and global attention surfaces as one keyed request. Its card always states the child and inherited policy.
- **Codex / ACP:** Correlate Codex child thread/turn/item ids or ACP session/tool-call ids with Integrator lineage.
- **Fallback:** PTY prompts get a synthetic request id scoped to process and input position.
- **Acceptance:** One response resolves all views, and a child can never offer a permission broader than its delegated maximum.

### 066 — Live grids do not reorder themselves

**Priority:** P1 · **Owner:** Client-owned spatial stability

- **Behavior:** Running, waiting, completed, and failed cards keep position while work is active. Sorting/repacking occurs only after explicit user sort or a settled batch.
- **Codex / ACP:** Status updates are asynchronous and can burst; neither protocol specifies visual order.
- **Fallback:** New children append to an available slot with a stable creation sequence.
- **Acceptance:** A user targeting Stop on card 7 cannot have another completion move a different card under the pointer/focus.

### 067 — Side questions state whether they are truly forked

**Priority:** P0 · **Owner:** Adapter-derived honesty

- **Behavior:** A side question says `Reads main task through Turn 6 · does not write to main context`. It is a popover for one exchange and promotes to a pane when longer.
- **Codex / ACP:** Codex supports `thread/fork` with an optional last-turn boundary and documents side/Btw flows. ACP session fork is still a Draft RFD, not a stable v1 assumption.
- **Fallback:** Create a separate session with an explicit provider-neutral context snapshot/handoff and label it `Snapshot, not native fork`.
- **Acceptance:** Closing/promoting a side question never injects messages into the parent unless the user previews and confirms promotion.

### 068 — Stop child never ambiguously stops the parent

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Child Stop names the child; Stop all is a separate parent action with a count and confirmation when destructive.
- **Codex / ACP:** Codex turn/thread ids allow targeted interruption; ACP cancellation is session-scoped, so target the child session only.
- **Fallback:** If a runtime multiplexes children without individual control, disable targeted Stop and explain `Runtime exposes only Stop all`.
- **Acceptance:** Protocol-call tests assert the exact child session/thread id and parent status remains unchanged.

### 069 — Candidate cards keep branch/worktree identity visible

**Priority:** P0 · **Owner:** Client-owned Git/orchestration

- **Behavior:** Best-of-N cards show candidate label, absolute checkout/worktree, branch, base, dirty state, and whether it is safe to delete.
- **Codex / ACP:** Codex can isolate tasks in worktrees and carries cwd/Git metadata. ACP session setup provides cwd but does not create worktrees; Integrator must orchestrate them.
- **Fallback:** A read-only/no-isolation candidate is visibly labeled and cannot enter write comparison mode.
- **Acceptance:** Accepting candidate B cannot stage, merge, or delete candidate A's checkout by path/branch confusion.

### 070 — Child completion returns a structured evidence envelope

**Priority:** P0 · **Owner:** Integrator delegation contract

- **Behavior:** Result includes outcome, summary, changed files, commands/tests, artifacts, commits, gaps, policy deviations, usage confidence, and recommended next action.
- **Codex / ACP:** Collect from Codex child thread/items or ACP session updates/tool diffs/terminals/plans/usage. The envelope is Integrator-owned and provider-neutral.
- **Fallback:** PTY adapters return a low-confidence transcript-derived envelope with missing fields explicitly marked.
- **Acceptance:** Parent never treats a prose `done` as verified completion without matching required evidence.

## 9. Lifecycle truth, recovery, authentication, and attention

### 071 — “Starting” is optimistic; “Running” is reconciled

**Priority:** P0 · **Owner:** Adapter-derived state machine

- **Behavior:** Immediately after submit show Starting. Promote to Running only after native thread/session and turn/prompt acceptance or first valid lifecycle event.
- **Codex / ACP:** Codex `turn/start` returns an initial turn and streams events. ACP `session/prompt` remains an outstanding request while updates arrive.
- **Fallback:** A PTY run becomes Running after process creation plus a verified prompt write, with lower control fidelity noted.
- **Acceptance:** Failed session creation cannot leave a phantom Running row or consume the draft.

### 072 — Interrupted, cancelled, process-killed, and cleaned up are separate

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Turn outcome, tool/process state, background terminals, worktree cleanup, and queued messages settle independently and are summarized together.
- **Codex / ACP:** Codex distinguishes turn interrupt and background-terminal/process termination. ACP distinguishes prompt cancellation from terminal kill/release.
- **Fallback:** Unknown sub-state remains Unknown with retry/inspect; do not collapse everything into Stopped.
- **Acceptance:** A cancelled turn with a still-running dev server shows exactly that and offers Stop server separately.

### 073 — A broken activity stream has its own visible state

**Priority:** P0 · **Owner:** Client-owned recovery

- **Behavior:** If events stop while process/native state may continue, show `Activity stream interrupted · last event 38s ago` with Reconnect, Open terminal, Stop through known channel, and Diagnostics.
- **Codex / ACP:** App-server connection/subscription, native turn state, and process state are separable. ACP transport loss does not prove the agent stopped.
- **Fallback:** Poll only supported status/list/output methods; otherwise retain Unknown rather than fabricate progress.
- **Acceptance:** Killing only the event transport never leaves indefinite `Thinking…`, and a live process remains controllable if another channel exists.

### 074 — Resume restores native context and local unsent state separately

**Priority:** P0 · **Owner:** Client-owned reconciliation

- **Behavior:** Resume/load restores native conversation into the transcript; Integrator then reapplies local view state and the unsent draft without adding it to model history.
- **Codex / ACP:** Codex `thread/resume` appends future turns; `thread/read` inspects without resuming. ACP stable session resume/load reconnects to native context and may replay history.
- **Fallback:** If resume is unsupported, offer New session with handoff while retaining the old task as read-only history.
- **Acceptance:** The last native user message and local unsent draft can coexist visibly and are never deduplicated/merged.

### 075 — Login detours return to the exact blocked action

**Priority:** P0 · **Owner:** Client-owned flow

- **Behavior:** Vendor login/OAuth/device flow preserves task, draft, picker state, scroll/focus, and intended action; success runs a health/capability refresh then returns.
- **Codex / ACP:** Codex exposes MCP OAuth and native login surfaces. ACP agents advertise auth methods during initialization and accept the selected method through `authenticate`.
- **Fallback:** Open vendor-owned terminal/browser instructions and provide `I've finished — recheck` without ever collecting a subscription password.
- **Acceptance:** Failed, cancelled, duplicate, and successful login paths all return to the same task with no auto-submit.

### 076 — Logout warns about ambiguous active-session behavior

**Priority:** P0 · **Owner:** Client-owned safety

- **Behavior:** Before logout, summarize active sessions/processes and state that the agent may terminate, retain, or later reject them unless its behavior is known.
- **Codex / ACP:** ACP stable logout explicitly leaves existing-session behavior implementation-defined. Codex logout clears credentials but active local/remote consequences should be checked per surface.
- **Fallback:** Offer Cancel, Stop active then logout, or Logout and leave tasks in Unknown/Reauth-needed state.
- **Acceptance:** Logout never silently marks active tasks complete or stopped.

### 077 — Runtime details show negotiated identity and capability age

**Priority:** P1 · **Owner:** Client-owned diagnostics

- **Behavior:** Details show executable/endpoint, agent/client title/name/version, protocol version, capability manifest, connection time, last health check, and adapter fidelity.
- **Codex / ACP:** Codex app-server has initialization/capability/version data. ACP `initialize` supports clientInfo/agentInfo and negotiated protocol/capabilities.
- **Fallback:** Missing implementation info is `Not supplied by agent`, not Integrator's package version.
- **Acceptance:** A support bundle can identify the exact agent and negotiated capability set without revealing credentials.

### 078 — Zero, none, unknown, unavailable, and not exposed are distinct

**Priority:** P0 · **Owner:** Client-owned language

- **Behavior:** `0` is measured zero; None is valid empty; Unknown is failed determination; Unavailable is currently unusable; Not exposed means the provider/protocol does not provide it; Stale includes timestamp.
- **Codex / ACP:** ACP optional cost/metadata/capabilities and Codex usage/capability surfaces make absence semantically important.
- **Fallback:** Never coerce null/missing/error to zero or Unlimited.
- **Acceptance:** Contract tests cover every absence state for usage, history, context, cost, exit code, Git, and capabilities.

### 079 — Offline steering waits for reconciliation before send

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Prompts composed offline are `Pending locally`, not queued at the runtime. On reconnect, refresh task state and ask/preview if the active turn or checkout changed.
- **Codex / ACP:** Neither a failed Codex `turn/steer` nor a disconnected ACP session guarantees delivery. ACP remote transport support is still evolving.
- **Fallback:** Offer Send as next turn, Start handoff session, Edit, or Discard.
- **Acceptance:** Reconnect never auto-sends text against a now-completed/failed/different turn.

### 080 — Notifications deep-link to the exact attention object

**Priority:** P0 · **Owner:** Client-owned

- **Behavior:** Approval, question, failure, and completion notifications carry task id plus turn/run/tool/request id and open the exact card with keyboard focus.
- **Codex / ACP:** Use Codex deep-link-compatible task ids plus app-owned fragments/state; ACP session/tool ids map through Integrator task identity.
- **Fallback:** If the event was removed/resolved, open the task at its outcome and say `This request is no longer active`.
- **Acceptance:** Clicking a notification from another project/window never lands at a generic home screen or the wrong task.

- **Behavior:** Press/shortcut begins Listening with waveform/timer and live accessible label; release/confirm processes; Escape cancels without changing the draft; inserted text remains editable before send.

- **Fallback:** When audio capability is absent, transcribe locally/OS-side if authorized or disable with a clear requirement; never stream microphone data unexpectedly.
- **Acceptance:** Microphone permission denial, device loss, silence, cancellation, and successful transcription preserve prior draft/selection.

### 090 — Path menus use native platform language and ordering

**Priority:** P1 · **Owner:** Client-owned

- **Behavior:** Use `Show in File Explorer` on Windows and `Show in Finder` on macOS; respect Open With/Services conventions; keep Attach/Open/Reveal/Copy actions consistently grouped.

- **Fallback:** On remote paths, replace Reveal with `Open remote folder` or `Copy remote path`; do not invoke a local shell with an invalid path.

### 097 — A compact usage meter represents exactly one dimension

### 098 — Config, policy, and extension metadata changes are auditable

**Priority:** P0 · **Owner:** Client-owned audit

- **Behavior:** Record who/what changed runtime option, permission, project policy, skill/plugin state, MCP config, or unknown extension metadata; show old/new, scope, source, and acknowledgment.

- **Fallback:** Preserve unknown `_meta` only in bounded diagnostics/storage with size/redaction limits and label it untrusted extension data.
- **Acceptance:** No custom metadata can grant permissions, select destructive behavior, render raw HTML, or bypass policy; relevant changes remain traceable.

### 099 — “Copy diagnostics” is useful and safe by default

**Priority:** P0 · **Owner:** Client-owned support

- **Fallback:** If files cannot be attached, copy a concise Markdown report and save larger redacted logs locally.
- **Acceptance:** Automated secret corpus finds no token, cookie, env value, prompt attachment contents, or home-directory personal data unless explicitly opted in.

### 100 — One action copies the current state for handoff or support

**Priority:** P0 · **Owner:** Client-owned synthesis

- **Fallback:** Missing native fields say Unknown/Not exposed; do not omit gaps in a way that implies success.
- **Acceptance:** A pasted state summary lets another human/runtime continue safely and matches the on-screen state at one captured timestamp.

## 12. Bootstrap, onboarding, runtime discovery, and environment health

### 101 — The shell appears before runtime probes finish

**Priority:** P0 · **Owner:** Client-owned orchestration

- **Behavior:** Render projects, drafts, cached tasks, and the composer immediately. Discover Codex, ACP agents, CLIs, authentication, models, plugins, and environment health in parallel with per-runtime progress instead of blocking the whole app behind one spinner.
- **Codex / ACP:** Codex exposes initialization and capability/catalog methods. ACP initialization negotiates protocol version and capabilities, but neither protocol owns the desktop bootstrap sequence.
- **Fallback:** A slow or broken adapter becomes an independently retryable row; healthy runtimes remain usable.
- **Acceptance:** With one probe hung for 30 seconds, cached navigation is interactive within 500 ms and another healthy runtime can start a task.

### 102 — Every detected runtime shows the executable actually in use

**Priority:** P0 · **Owner:** Adapter-derived

- **Behavior:** Show resolved executable path, version, launch source, transport, and last successful probe. Distinguish PATH discovery, configured path, bundled runtime, WSL, remote host, and compatibility shim.
- **Codex / ACP:** Codex initialization/implementation metadata and ACP `agentInfo` help identify a runtime, but the host must also record the process it launched.
- **Fallback:** If the runtime withholds version metadata, show the executable fingerprint and `Version not reported`; never infer identity from branding alone.
- **Acceptance:** Two installed versions cannot silently swap after restart or PATH change; diagnostics and the runtime picker name the same resolved process.

### 103 — Version mismatch is a compatibility state, not a generic failure

**Priority:** P0 · **Owner:** Adapter-derived compatibility

- **Behavior:** Classify a runtime as compatible, degraded, too old, too new/unverified, or failed. Name the missing or changed primitives and offer the smallest safe remedy.
- **Codex / ACP:** Codex app-server schemas and ACP version negotiation/capabilities supply the evidence; adapter releases define tested ranges.
- **Fallback:** Unknown future versions may run only through negotiated capabilities and conservative fallbacks, with experimental behavior visibly labeled.
- **Acceptance:** A fixture missing session listing but supporting prompt turns opens in degraded mode with history disabled, not as `Offline` or falsely `Fully supported`.

### 104 — Authentication names the account, workspace, and credential kind

**Priority:** P0 · **Owner:** Adapter-derived identity

- **Behavior:** A runtime row says whether it uses a ChatGPT subscription login, workspace access token, API key, vendor account, local model, or inherited CLI session, and shows the non-secret account/workspace identity when available.
- **Codex / ACP:** Codex and ACP expose authentication methods/status, but subscription entitlements and API billing are not interchangeable.
- **Fallback:** Show `Authenticated — identity not exposed` rather than guessing an email, plan, billing source, or quota owner.
- **Acceptance:** A user can tell which account will pay or consume quota before sending, and no credential material appears in the UI, logs, or copied diagnostics.

### 105 — Login returns to the interrupted intent

**Priority:** P0 · **Owner:** Client-owned navigation

- **Behavior:** Preserve the draft, selected runtime, project, attachments, and requested action through browser/device-code/OAuth login, then return focus to the exact control that required authentication.
- **Codex / ACP:** Codex auth flows and ACP `authenticate` may leave the client for an external flow; the client owns continuation state.
- **Fallback:** If callback correlation is lost, keep the draft and show a safe `Check login status` action on the originating runtime.
- **Acceptance:** Starting login from Send never lands on a blank home screen or sends automatically when authentication completes.

### 106 — Project trust is explicit, scoped, and reversible

**Priority:** P0 · **Owner:** Client-owned policy UI

- **Behavior:** Explain what trust enables—project config, instructions, hooks, plugins, commands, or broader file access—before granting it. Display the trusted path and let users revoke trust without deleting the project.
- **Codex / ACP:** Codex skips project-local `.codex` layers in untrusted projects. ACP has filesystem capabilities but no cross-agent project-trust standard.
- **Fallback:** Open untrusted projects with project-local executable customization disabled and a precise `Skipped because untrusted` explanation.
- **Acceptance:** Trusting one worktree does not trust its parent drive, sibling checkout, symlink target, or another runtime unless explicitly stated.

### 107 — Imports begin with a dry-run and a conflict map

**Priority:** P0 · **Owner:** Client-owned migration

- **Behavior:** Before importing another agent, show detected instructions, settings, projects, recent tasks, skills, plugins, MCP servers, hooks, slash commands, and subagent definitions; mark add, merge, replace, skip, unsupported, and secret-bearing fields separately.
- **Codex / ACP:** Codex documents importable agent data. ACP does not define configuration migration, so this is client/adapter work.
- **Fallback:** Unsupported structures are copied to a quarantined reference bundle or left untouched, never flattened into misleading equivalents.
- **Acceptance:** Cancel changes nothing; confirm produces a receipt listing each source, destination, conflict decision, redaction, and item requiring review.

### 108 — Runtime installation is resumable and inspectable

**Priority:** P1 · **Owner:** Client-owned installer

- **Behavior:** Show download, verification, install, first launch, authentication, and capability probe as distinct stages with current work, elapsed time, cancel safety, and a bounded log drawer.
- **Codex / ACP:** Installation sits below both protocols; initialization only verifies the result.
- **Fallback:** If automatic installation is unsupported, provide a copyable official command and re-probe button without pretending the app controls the external installer.
- **Acceptance:** Closing and reopening during a download or failed install yields a recoverable stage, not a permanent spinner or duplicate installation.

### 109 — Environment health errors point to the failing layer

**Priority:** P0 · **Owner:** Adapter-derived diagnostics

- **Behavior:** Separate runtime process, transport, authentication, shell, Git, project path, filesystem, network, MCP, and policy health. Each failure includes evidence timestamp, effect, and scoped repair action.
- **Codex / ACP:** Codex startup/MCP/config status and ACP initialization/session errors provide structured signals; adapter probes fill transport and executable gaps.
- **Fallback:** Preserve raw bounded error details behind `Details` while leading with a plain-language diagnosis and safe retry.
- **Acceptance:** `Executable missing`, `OAuth expired`, `project path inaccessible`, and `MCP server failed` never collapse into the same red dot or toast.

### 110 — First run ends with a reversible smoke test

**Priority:** P1 · **Owner:** Client-owned onboarding

- **Behavior:** Offer a tiny read-only or disposable-sandbox task that verifies prompt streaming, cancellation, tool rendering, permissions, files, and terminal support for the chosen runtime without modifying a real repository.
- **Codex / ACP:** Use negotiated Codex/ACP primitives only; the test result becomes a capability-specific health report, not a benchmark score.
- **Fallback:** Runtimes without a disposable environment run a no-tool prompt plus explicit manual checks.
- **Acceptance:** The smoke test can be skipped, cancelled, rerun, and fully cleaned up; its session is labeled diagnostic and excluded from normal task history by default.

## 13. Instructions, skills, plugins, hooks, MCP, and extensibility

### 111 — The effective instruction stack is visible in precedence order

**Priority:** P0 · **Owner:** Adapter-derived instruction inspector

- **Behavior:** Show system/managed policy, user instructions, project-root guidance, nested directory guidance, task instructions, skill instructions, and temporary overrides in the order actually applied, with source paths and active scope.
- **Codex / ACP:** Codex documents layered `AGENTS.md` and configuration. ACP carries prompts/content but does not standardize host instruction discovery.
- **Fallback:** If an agent will not expose its composed prompt, show the client-known layers and label vendor-internal instructions `Not exposed`.
- **Acceptance:** Selecting a file in a nested directory updates the inspector without implying that inactive parent/sibling instructions are active.

### 112 — Mid-task instruction changes have an explicit activation boundary

**Priority:** P0 · **Owner:** Client-owned consistency

- **Behavior:** When an active instruction file, skill, hook, or policy changes, show what changed and whether it affects the next tool, next turn, resumed session, or only a new session. Offer reload/restart/fork when semantics require it.
- **Codex / ACP:** Codex exposes filesystem/config/skill change signals. ACP agents may send configuration updates but define no universal instruction reload boundary.
- **Fallback:** Assume `new turn only` or `new session required` conservatively and label the assumption.
- **Acceptance:** A task never silently claims to follow guidance that changed after its effective context snapshot.

### 113 — Skill cards show provenance, scope, and dependencies

**Priority:** P0 · **Owner:** Adapter-derived catalog

- **Behavior:** Each skill shows name, purpose, source, installed version/commit, personal/workspace/project scope, entrypoint, required tools/apps/MCP servers, compatible runtimes, and whether it was explicitly invoked or auto-selected.
- **Codex / ACP:** Codex exposes skill listing/config/change methods. ACP has no standard skill registry, so non-Codex agents require adapters or instruction-based shims.
- **Fallback:** A filesystem-discovered skill with incomplete metadata is labeled `Unverified local skill`; do not fabricate compatibility.
- **Acceptance:** Two same-named skills remain distinguishable and the task transcript records which immutable source/version ran.

### 114 — Skill enablement is scoped and conflict-aware

**Priority:** P0 · **Owner:** Client-owned policy

- **Behavior:** Enable/disable at personal, workspace, project, or task scope; display inherited state and warn when two active skills claim the same explicit trigger, command, or destination.
- **Codex / ACP:** Codex supports per-skill config, while adapters normalize other agents' skills. ACP sessions do not own persistent skill configuration.
- **Fallback:** When runtime-level toggling is unavailable, gate injection on the client and clearly say the underlying CLI may still discover its own skills.
- **Acceptance:** Disabling a skill for one task neither edits its files nor disables it globally, and effective state is unchanged after restart.

### 115 — Skill reload is diffable and never swaps code mid-action

**Priority:** P1 · **Owner:** Client-owned lifecycle

- **Behavior:** Detect added, removed, and changed skills; show metadata/instruction diffs and activate the new version only at a safe boundary. Keep the version used by prior turns inspectable.
- **Codex / ACP:** Codex exposes skill-change notifications. ACP has no equivalent, so adapters watch declared sources.
- **Fallback:** If safe hot reload cannot be proven, require a new task/session and preserve the current task's pinned version.
- **Acceptance:** Editing `SKILL.md` during a tool call cannot cause half the call to use old guidance and half to use new guidance.

### 116 — Plugin install previews the whole bundle and its reach

**Priority:** P0 · **Owner:** Client-owned extension security

- **Behavior:** Before install, show source, publisher/signing state, version, files, skills, MCP servers, hooks, apps, commands, requested paths/network destinations, default approval modes, and workspace sharing scope.
- **Codex / ACP:** Codex plugins can bundle skills, hooks, apps, and MCP configuration. ACP does not define a plugin package.
- **Fallback:** Local/unsigned bundles remain installable only behind an explicit provenance warning and exact-source review.
- **Acceptance:** Install confirmation cannot be completed from a name/logo-only card; the receipt records the reviewed manifest hash.

### 117 — Plugin updates preserve choices but re-review new authority

**Priority:** P0 · **Owner:** Client-owned extension lifecycle

- **Behavior:** Show version diff and preserve compatible enablement/config. Require renewed review when hooks, executable commands, MCP identities, tool allowlists, external origins, or permission defaults change.
- **Codex / ACP:** Codex plugin and hook trust are definition-sensitive; ACP cannot represent this package lifecycle.
- **Fallback:** If a reliable semantic diff is impossible, stage the update disabled and require full review.
- **Acceptance:** A cosmetic metadata update does not erase settings, while a changed executable or network origin cannot become active through one-click background update.

### 118 — Hook trust is tied to the exact definition

**Priority:** P0 · **Owner:** Codex-native policy UI

- **Behavior:** List hook event, matcher, command, source layer, managed state, timeout, working directory, and hash. Changed non-managed hooks are skipped until the new definition is reviewed; show a diff from the previously trusted version.
- **Codex / ACP:** Codex explicitly hashes hook definitions, merges matching sources, and distinguishes managed hooks. ACP has no hook primitive.
- **Fallback:** For other CLIs, run client-managed hooks only through the Integrator trust store and label vendor-internal hooks separately.
- **Acceptance:** Trust does not survive a one-character command change; a managed hook is visibly policy-locked and cannot masquerade as user-approved.

### 119 — MCP startup is a timeline, not a single green dot

**Priority:** P0 · **Owner:** Adapter-derived MCP manager

- **Behavior:** For each server show configured source, transport/command or origin, starting, authenticating, discovering, ready, degraded, failed, reconnecting, and stopped states; include tool/resource counts, elapsed time, last error, retry, logs, and OAuth action.
- **Codex / ACP:** Codex exposes MCP server status, startup status, OAuth, tools/resources, and elicitation. ACP can pass MCP server definitions at session setup but does not standardize a global manager UI.
- **Fallback:** PTY-only CLIs expose parsed status with `Approximate` confidence and raw bounded logs.
- **Acceptance:** One failed MCP server does not block unrelated servers or the base agent, and reconnect never briefly reports stale `Ready`.

### 120 — MCP authority is controllable per server and per tool

**Priority:** P0 · **Owner:** Client-owned policy normalization

- **Behavior:** Let users enable a server, allow/deny specific tools, choose approval behavior, inspect tool schemas and safety hints, and see policy/manifest/runtime source. Dynamic tool changes require review when they expand authority.
- **Codex / ACP:** Codex supports enabled/disabled tool lists and per-tool approval modes for configured/plugin MCP servers. ACP negotiates client MCP transport support but does not standardize these policy controls.
- **Fallback:** If the runtime only accepts all-or-nothing MCP configuration, expose only that coarse control and state the loss of granularity.
- **Acceptance:** A newly discovered write tool never inherits approval-free access merely because its server was previously approved for read tools.

## 14. Settings, policy provenance, customization, and migration

### 121 — Every consequential setting answers “why is this value active?”

**Priority:** P0 · **Owner:** Client-owned settings model

- **Behavior:** Show effective value plus source layer: built-in default, runtime default, personal, workspace, project, task, plugin, environment, command line, managed requirement, or temporary session override.
- **Codex / ACP:** Codex has layered config and requirements; ACP configuration options expose current session choices but not a universal persistent-source model.
- **Fallback:** Unknown runtime provenance is labeled `Reported by agent — source not exposed`.
- **Acceptance:** Model, effort, permissions, network, skill/plugin, tool, and privacy settings never display an unexplained value when multiple layers can affect them.

### 122 — Reset means “inherit,” not “write the default again”

**Priority:** P0 · **Owner:** Client-owned settings model

- **Behavior:** Distinguish inherited, explicitly overridden, and policy-forced values. `Reset` removes the selected scope's override, previews the newly inherited value, and supports undo.
- **Codex / ACP:** Codex config writes operate on layered configuration. ACP `session/set_config_option` sets session state but does not remove arbitrary host persistence.
- **Fallback:** Where deletion is unsupported, offer `Use runtime default` and disclose that it writes an explicit value.
- **Acceptance:** Changing a global default later affects scopes that inherited it but not scopes with intentional overrides.

### 123 — Scope selection defaults to the narrowest useful blast radius

**Priority:** P0 · **Owner:** Client-owned safety

- **Behavior:** A settings edit names where it will apply and how many projects/tasks/runtimes it affects. Default task-only for experimental runtime choices and project-only for repo-specific instructions/tools unless the user deliberately broadens scope.
- **Codex / ACP:** Codex layers and ACP session config supply different persistence boundaries; Integrator presents them consistently without pretending they are equivalent.
- **Fallback:** If an adapter only supports global config, warn before writing and offer a client-side task override when safe.
- **Acceptance:** A permission or tool change cannot silently widen from one task to every project through an ambiguous toggle.

### 124 — Settings search understands aliases and returns users to their work

**Priority:** P1 · **Owner:** Client-owned navigation

- **Behavior:** Search labels, descriptions, config keys, runtime terminology, old names, and common synonyms. Deep links highlight the target setting and Back returns to the originating error, permission, plugin, or task.
- **Codex / ACP:** Codex exposes canonical config keys; adapters contribute vendor aliases. The navigation contract is client-owned.
- **Fallback:** Unknown keys open a raw-config search with source paths and schema help.
- **Acceptance:** Searching `thinking`, `reasoning`, `effort`, or the native key reaches the same model-control family without losing the caller's draft or scroll.

### 125 — Invalid settings remain editable and explain the exact boundary

**Priority:** P0 · **Owner:** Client-owned form state

- **Behavior:** Validate syntax and semantics inline, preserve the user's invalid draft, identify the offending token/range, show allowed forms, and keep the last valid effective value active until Apply succeeds.
- **Codex / ACP:** Codex config/schema errors and ACP request errors provide evidence, but the client owns non-destructive editing.
- **Fallback:** If only runtime validation exists, debounce a dry validation request and never write on blur.
- **Acceptance:** A malformed path, regex, schedule, model id, or permission rule cannot corrupt config or disappear after an error.

### 126 — Multi-setting changes apply atomically or show partial reality

**Priority:** P0 · **Owner:** Client-owned transaction layer

- **Behavior:** Preview a settings batch, validate all fields, apply with rollback where possible, and show per-field results if the runtime cannot transact. Never toast `Saved` while some fields failed.
- **Codex / ACP:** Codex offers config writes but adapter/runtime boundaries may not share a transaction. ACP config changes are individual requests returning full state.
- **Fallback:** Serialize writes, re-read effective state, and produce a recovery patch for failed fields.
- **Acceptance:** Killing the app midway through a batch yields either the old state, the complete new state, or an explicit reconciled partial receipt after restart.

### 127 — Restart requirements name what must restart

**Priority:** P1 · **Owner:** Adapter-derived lifecycle

- **Behavior:** Distinguish no restart, reload view, reconnect adapter, restart runtime process, start new session, reopen project, or restart app. Let users postpone and show pending changes where they matter.
- **Codex / ACP:** Capabilities and configuration responses reveal some live changes; adapter metadata defines remaining activation boundaries.
- **Fallback:** Use the smallest conservative boundary and say it is conservative.
- **Acceptance:** `Restart required` never forces a whole-app restart when a runtime reconnect suffices, and postponing cannot make the UI claim a not-yet-active value.

### 128 — External config edits trigger a three-way merge, not a tug-of-war

**Priority:** P0 · **Owner:** Client-owned config watcher

- **Behavior:** Watch active config/instruction files. If disk changes while the settings UI has unsaved edits, compare base, local draft, and disk; auto-merge independent fields and ask on conflicts.
- **Codex / ACP:** Codex exposes config/filesystem change signals. ACP has no persistent config-file standard.
- **Fallback:** On runtimes without watches, re-read and compare before every write.
- **Acceptance:** Editing `config.toml` in an external editor cannot be silently overwritten by a stale Integrator settings panel.

### 129 — Managed policy is visibly locked and explains the constraint

**Priority:** P0 · **Owner:** Client-owned enterprise policy UI

- **Behavior:** Locked controls show enforced value, policy source, optional administrator rationale, affected scope, and which less-restrictive local values were ignored. Users can copy a support-safe policy summary.
- **Codex / ACP:** Codex `requirements.toml` and managed configuration can pin features, hooks, permissions, MCP identities, plugins, and apps. ACP does not define enterprise policy provenance.
- **Fallback:** Vendor restrictions with no source metadata show `Managed by runtime/workspace`; they are never presented as a UI bug.
- **Acceptance:** A user cannot toggle a locked control into a visually enabled but operationally ignored state.

### 130 — Settings export is reproducible, previewable, and secret-safe

**Priority:** P1 · **Owner:** Client-owned migration

- **Behavior:** Export selected scopes as a versioned manifest with runtime/adapter compatibility, omitted-secret markers, source references, and hashes. Import shows a field-level plan before writing.
- **Codex / ACP:** Codex schemas/config files can be represented; ACP session configuration requires adapter-specific mapping and cannot promise persistent parity.
- **Fallback:** Unsupported values remain preserved as namespaced metadata with a warning, not coerced into a nearby setting.
- **Acceptance:** Round-tripping on the same supported version reproduces non-secret effective settings, while automated scans find no token, cookie, password, or environment secret.

## 15. Tabs, panes, windows, layout, and focus continuity

### 131 — Preview tabs and committed tabs behave differently

**Priority:** P1 · **Owner:** Client-owned workspace

- **Fallback:** On compact/mobile layouts, use one preview surface with a clear Pin/Open action.

### 132 — Closing a tab respects unsaved and generated state

**Priority:** P0 · **Owner:** Client-owned workspace

- **Fallback:** If dirty state cannot be confirmed, preserve a recovery snapshot and say `State uncertain` before discard.
- **Acceptance:** One generic `Discard changes?` dialog is never used for unrelated terminal, file, annotation, and artifact risks.

### 133 — Tab overflow always reveals the active item

**Priority:** P1 · **Owner:** Client-owned layout

- **Behavior:** Keep the active tab visible, provide keyboard-accessible overflow search, preserve stable order, show dirty/running/attention state in the overflow list, and avoid compressing labels below recognition.

- **Fallback:** At very narrow widths, replace the strip with an active-title selector without losing shortcuts.

### 134 — Drag targets preview the resulting layout before drop

**Priority:** P1 · **Owner:** Client-owned direct manipulation

### 135 — Pane resizers are clamped, resettable, and keyboard operable

- **Behavior:** Enforce per-pane minimums, show a larger invisible hit target, support arrow-key resizing with modifiers, double-click reset, and announce size changes. Persist logical sizes, not raw pixels alone.
- **Codex / ACP:** No protocol ownership. GitHub Desktop's resizer patterns provide source-level precedent.
- **Fallback:** If a pane cannot satisfy minimums, collapse it into a tab/drawer instead of overlaying primary content.
- **Acceptance:** Resizing at 100–200% zoom, with touch, pointer, and keyboard never strands controls off-screen; reset returns to a documented default.

### 136 — Automatic collapse never overwrites a user's layout choice

**Priority:** P0 · **Owner:** Client-owned responsive state

- **Behavior:** Track whether a sidebar/panel collapsed due to viewport pressure or explicit user action. Auto-expand only panels the layout auto-collapsed; remember user choices per workspace/layout class.
- **Codex / ACP:** No protocol primitive. Goose's system-versus-user collapse distinction is the reference behavior.
- **Fallback:** If state provenance is lost, keep the current layout rather than surprising the user with an expansion.
- **Acceptance:** Narrowing then widening a window restores an auto-collapsed sidebar, while one the user closed stays closed.

### 137 — Transient UI restores focus to the invoking control

**Priority:** P0 · **Owner:** Client-owned accessibility

- **Behavior:** Dialogs, command palettes, menus, permission sheets, file pickers, and popovers record the logical invoker. Closing by completion, Escape, outside click, or error restores focus if it still exists; otherwise use the nearest stable fallback.
- **Codex / ACP:** Approval/elicitation events create some transient surfaces, but focus remains client-owned.
- **Fallback:** If the original item disappeared, focus the containing list/region and announce the state change.
- **Acceptance:** Keyboard-only loops never fall to the document body, title bar, or a hidden element after a transient surface closes.

### 138 — Task view state and global preferences are separate

**Priority:** P0 · **Owner:** Client-owned persistence

- **Behavior:** Persist task-local scroll, selected file, diff mode, open artifact, plan expansion, terminal selection, and browser route separately from global density, theme, font, keymap, and pane defaults.
- **Codex / ACP:** Native session ids anchor task-local state; neither protocol should receive irrelevant presentation preferences.
- **Fallback:** If a task id changes through import/fork, copy view state only when lineage is proven.
- **Acceptance:** Opening Task B cannot inherit Task A's file/scroll, while changing global density updates both without corrupting their local positions.

### 139 — A running task has one control owner across windows

**Priority:** P0 · **Owner:** Client-owned multi-window coordination

- **Behavior:** Multiple windows may observe one task, but only one control lease sends, steers, interrupts, answers permissions, or mutates its checkout at a time. Other windows show owner and can request/take control explicitly.
- **Codex / ACP:** Codex/ACP session ids support multiple views but do not guarantee desktop control arbitration.
- **Fallback:** Without a lease service, enforce a same-machine process lock and make other views read-only.
- **Acceptance:** Two windows cannot submit conflicting approval responses or duplicate a queued prompt; takeover is logged and immediately reflected everywhere.

### 140 — Window close and app quit distinguish UI lifetime from task lifetime

**Priority:** P0 · **Owner:** Client-owned lifecycle

- **Behavior:** Closing a window with running local, remote, scheduled, or detached work lists what continues, what requires the host, and what will stop. Offer Keep running, Stop safely, or Cancel close according to actual capability.
- **Codex / ACP:** Codex thread/runtime status and ACP session close/cancel inform behavior; neither makes all work durable after process exit.
- **Fallback:** If continuation cannot be guaranteed, do not offer `Keep running`; provide an exact handoff/stop summary.
- **Acceptance:** OS quit, last-window close, forced update, and session sign-out each have tested behavior and never silently abandon a task that the UI claimed would continue.

## 16. Browser, preview, Computer Use, annotations, and downloads

### 141 — Browser identity is visibly separate from the user's normal browser

**Priority:** P0 · **Owner:** Client-owned browser chrome

- **Behavior:** Show whether a tab uses the isolated in-app profile, a connected Chrome profile, a disposable test profile, or remote browser. Account/avatar indicators and cookie/storage controls belong to that profile, not to the agent runtime account.
- **Codex / ACP:** Codex documents a separate in-app browser profile and a Chrome extension for existing sessions. ACP has no browser-profile primitive.
- **Fallback:** Browser adapters that cannot expose profile identity must show `Profile identity unavailable` before authenticated actions.
- **Acceptance:** A user cannot mistake being signed into ChatGPT/Codex for being signed into the website, or mistake an isolated browser for their regular Chrome session.

### 142 — Website permission is origin-scoped, reviewable, and expirable

**Priority:** P0 · **Owner:** Client-owned browser policy

- **Behavior:** Grant Computer Use to an exact scheme/host/port with Allow once, Until task ends, or Remember choices. Display allowed/blocked sites, last use, profile, and revoke controls; treat redirects and subdomains as new origins unless covered explicitly.
- **Codex / ACP:** Codex browser use asks before website interaction and exposes settings for allowed/blocked sites. ACP tool permissions can inspire option semantics but do not define web origins.
- **Fallback:** Unclassifiable/custom-scheme pages remain manual-only.
- **Acceptance:** Allowing `http://localhost:3000` does not allow `http://localhost:3001`, `https://localhost:3000`, or a redirect to an external domain.

### 143 — Sensitive actions ask at the action boundary

**Priority:** P0 · **Owner:** Client-owned safety

- **Behavior:** A site-level allow does not pre-approve submitting personal data, purchasing, sending, publishing, changing permissions, deleting, uploading, or confirming irreversible external state. The prompt shows target, changed fields, consequence, and whether retry could duplicate the action.
- **Codex / ACP:** Codex explicitly calls out confirmations for sensitive browser actions. ACP permissions provide general option patterns only.
- **Fallback:** If the adapter cannot identify a sensitive boundary reliably, pause before final form submission or destructive click and require human takeover.
- **Acceptance:** Approving navigation on a storefront cannot authorize checkout, and approval content is captured without exposing sensitive form values in logs.

### 144 — Human takeover has an unambiguous control handoff

**Priority:** P0 · **Owner:** Client-owned control arbitration

- **Behavior:** Clicking/type-to-take-over pauses agent input, displays `You control this page`, and prevents races. Resume shows the page/profile/origin and summarizes state changes made during takeover before the agent acts again.
- **Codex / ACP:** Computer Use supplies the automation channel; control ownership is a client concern.
- **Fallback:** For adapters that cannot pause granularly, interrupt the browser tool call and require a new action after takeover.
- **Acceptance:** Agent and user input can never interleave into the same form field or click sequence; takeover and resume are visible in the transcript.

### 145 — Local preview startup is observable and route-aware

**Priority:** P0 · **Owner:** Adapter-derived local preview

- **Behavior:** Detect known development-server URLs from structured terminal output, bind them to the owning task/process, show starting/ready/failed/port-changed state, and open the intended route only after readiness.
- **Codex / ACP:** Codex integrates terminals and browser preview. ACP terminal output/reference primitives can support detection, but no standard declares dev-server readiness.
- **Fallback:** Let the user enter a URL and attach it to a process; show connection retries with the last network error.
- **Acceptance:** A stale URL from a previous process is not opened as current, and port fallback from 3000 to 3001 updates the route without duplicate tabs.

### 146 — Browser tabs remember review-relevant viewport state

**Priority:** P1 · **Owner:** Client-owned browser state

- **Behavior:** Persist task, profile, URL, navigation history, viewport preset/dimensions, zoom, device scale, scroll, selected responsive state, and active annotation mode. Restore only after confirming the page can be safely revisited.
- **Codex / ACP:** No ACP primitive; Codex browser surface provides the native feature but client state defines continuity.
- **Fallback:** Authenticated or non-idempotent pages restore as a stale screenshot plus `Reload manually`, not an automatic navigation.
- **Acceptance:** Returning from a diff preserves the exact mobile viewport and scroll target used to report a visual bug.

### 147 — Reconnect preserves the last frame but labels it stale

**Priority:** P0 · **Owner:** Client-owned recovery

- **Behavior:** On browser/process/remote disconnection, keep the last screenshot/DOM-derived view for orientation, overlay disconnected state and timestamp, disable mutating controls, and reconcile URL/tabs/ownership after reconnect.
- **Codex / ACP:** Codex changelog and browser diagnostics include reconnect behavior; no generic ACP browser state exists.
- **Fallback:** If reconciliation fails, start a new browser instance while preserving the old view as an evidence artifact.
- **Acceptance:** A frozen frame can never look interactive or current, and reconnect cannot replay a pre-disconnect click or form submission.

### 148 — Annotations carry enough evidence to survive page drift

**Priority:** P0 · **Owner:** Client-owned annotation model

- **Behavior:** Store comment text, route, query, viewport, zoom, screenshot crop, DOM selector/signature when available, coordinates, selected bounds, timestamp, and page/build identity. Show whether the target is exact, relocated, ambiguous, or missing.
- **Codex / ACP:** Codex browser comments and adjustment controls provide the workflow. ACP content/resources can transport evidence but do not standardize annotations.
- **Fallback:** Coordinate-only annotations pin to the captured screenshot and require manual reattachment after layout change.
- **Acceptance:** After a DOM reorder, a comment never silently jumps to a visually similar but wrong element; ambiguity is explicit.

### 149 — Downloads have durable progress and destination semantics

**Priority:** P0 · **Owner:** Client-owned browser/filesystem

- **Behavior:** Show filename, origin, size, destination, progress, scan/policy state, pause/cancel where supported, completion, reveal/open, collision choice, and task association. Respect Ask where to save and the configured profile destination.
- **Codex / ACP:** Codex documents browser download location and prompt behavior. ACP file-system methods do not define browser downloads.
- **Fallback:** If only final completion is observable, show indeterminate progress and never claim a byte count.
- **Acceptance:** Interrupted downloads remain `.partial`/quarantined, duplicate names do not overwrite silently, and opening a dangerous type requires OS-appropriate warning.

### 150 — Developer/CDP access is a separate high-sensitivity mode

**Priority:** P0 · **Owner:** Client-owned browser security

- **Behavior:** Full developer access shows the exact profile/site, requested capabilities (DOM, console, network, runtime, performance), duration, policy source, and possible sensitive exposure. Console/network views redact secrets and support bounded export.
- **Codex / ACP:** Codex Developer mode grants controlled full Chrome DevTools Protocol access and requires explicit approval; managed policy may disable it.
- **Fallback:** Use screenshot/DOM-safe inspection when full CDP is unavailable or declined, and state the diagnostic limitation.
- **Acceptance:** Ordinary browser permission cannot silently escalate to CDP; each new origin/profile context requires policy-consistent approval and audit.

## 17. Scheduled, background, remote, and long-running work

### 151 — Schedules always show timezone, DST behavior, and the next real instant

**Priority:** P0 · **Owner:** Client-owned scheduler UI

- **Behavior:** Display human recurrence, IANA timezone, next three absolute run times with UTC offsets, and DST exception behavior before save. Editing system timezone never silently changes a schedule's meaning.
- **Codex / ACP:** Codex thread automations can wake the same thread on a schedule; ACP has no stable scheduler primitive.
- **Fallback:** Adapter-specific or OS schedules are represented through a normalized manifest plus their native identifier.
- **Acceptance:** Spring-forward missing times and fall-back duplicated times have an explicit skip/run-once/run-twice policy test.

### 152 — Missed runs follow a declared catch-up policy

**Priority:** P0 · **Owner:** Client-owned scheduling policy

- **Behavior:** Choose Skip, Run once when available, or Replay each missed occurrence with a safe maximum. Show the original due time and actual start time in history.
- **Codex / ACP:** Codex automation wakeups provide execution; catch-up semantics must be explicit in Integrator unless a native scheduler guarantees them.
- **Fallback:** Unknown native behavior is labeled and defaults to no automatic replay for state-changing tasks.
- **Acceptance:** Waking a laptop after five missed intervals cannot launch five overlapping write-capable runs without an explicit replay policy.

### 153 — Overlapping runs have an intentional concurrency rule

**Priority:** P0 · **Owner:** Client-owned scheduling policy

- **Behavior:** Per automation choose Skip new, Queue one, Queue all with cap, Cancel/replace prior, or Allow concurrent. Explain checkout, branch, file, rate-limit, and external-side-effect risks.
- **Codex / ACP:** Thread status and normalized runtime state detect active work; ACP does not define scheduled overlap.
- **Fallback:** Default to Skip new for write-capable work and Queue one for read-only monitoring.
- **Acceptance:** A slow hourly job cannot unknowingly stack multiple agents against the same working tree.

### 154 — Sleep, logout, offline, and host shutdown are different states

**Priority:** P0 · **Owner:** Client-owned lifecycle

- **Behavior:** State whether work runs in the local app, tray/background host, remote service, or vendor cloud. For each, explain what happens during screen lock, sleep, logout, network loss, app update, and shutdown.
- **Codex / ACP:** Codex local/cloud/remote environments differ; ACP local subprocess transport dies with its host unless separately supervised.
- **Fallback:** If durability is unknown, describe the task as host-dependent and offer a move/handoff option before exit.
- **Acceptance:** `Runs in background` is never used for work that actually stops when the last window or local agent process closes.

### 155 — A scheduled run records and checks its environment snapshot

**Priority:** P0 · **Owner:** Adapter-derived preflight

- **Behavior:** Record project path, repository/remote, branch/ref, worktree, runtime/adapter version, selected model/config, instruction/skill/plugin set, and relevant non-secret environment fingerprint. Compare at run time and classify drift.
- **Codex / ACP:** Codex thread/project/config state and ACP session/config metadata contribute; Integrator owns durable comparison.
- **Fallback:** Unavailable fields are explicit and high-risk drift blocks mutation until reviewed.
- **Acceptance:** A branch deletion, moved folder, changed remote, disabled skill, or downgraded runtime cannot be mistaken for the environment in which the schedule was approved.

### 156 — Credentials are preflighted without exposing or “testing” side effects

**Priority:** P0 · **Owner:** Adapter-derived auth health

- **Behavior:** Before unattended execution, verify that required runtime, MCP, remote-host, and external-service credentials are present, unexpired when knowable, scoped correctly, and available to the execution host.
- **Codex / ACP:** Codex/ACP auth and MCP status can provide non-secret readiness; adapter-specific services add scoped checks.
- **Fallback:** Unknown validity becomes `Will require sign-in` and blocks unattended write work rather than prompting invisibly.
- **Acceptance:** Preflight never prints credentials or performs a charge, message, publish, deployment, or other externally visible “test.”

### 157 — Scheduled approval mode is fixed, visible, and safe unattended

**Priority:** P0 · **Owner:** Client-owned permission policy

- **Behavior:** Persist the exact approval/permission profile with the automation, show its source and next-run effect, and define what happens when a new approval is required: block and notify, use a narrower fallback, or skip.
- **Codex / ACP:** Codex scheduled automations honor selected approval mode; ACP permission requests require a live response and do not imply unattended approval.
- **Fallback:** No responder means reject/blocked, never implicit approval or permission weakening.
- **Acceptance:** Changing the originating task's current permission selector does not silently change an already-saved automation.

### 158 — Cancelling a run does not accidentally disable its schedule

**Priority:** P0 · **Owner:** Client-owned lifecycle

- **Behavior:** Distinguish Cancel current run, Skip next run, Pause schedule, Disable schedule, and Delete automation. Confirm only destructive scope and show whether cleanup/rollback continues after cancellation.
- **Codex / ACP:** Codex turn/thread automation state and ACP cancellation/stop reasons map to the current run; recurring state remains client/native-scheduler data.
- **Fallback:** If native APIs conflate actions, expose only the operations that can be represented truthfully.
- **Acceptance:** Stopping a stuck run leaves future recurrence unchanged unless the user explicitly pauses/disables/deletes it.

### 159 — Automation history summarizes outcomes without notification spam

**Priority:** P1 · **Owner:** Client-owned history/notifications

- **Behavior:** Keep per-run due/start/end times, outcome, changes, approvals, usage confidence, artifacts, errors, and handoff. Group repeated unchanged monitoring results and notify only on configured transitions or thresholds.
- **Codex / ACP:** Codex task output and ACP turns/tools/usage provide run evidence; Integrator owns recurrence grouping and retention.
- **Fallback:** Store a bounded summary plus link to native history when full transcript retention is unavailable.
- **Acceptance:** Ten identical `No change` runs occupy one expandable group while the first failure or detected change creates visible attention.

### 160 — Remote control and remote execution have explicit ownership

**Priority:** P0 · **Owner:** Client-owned remote coordination

- **Behavior:** Show execution host, observing device, control owner, connection quality, last acknowledged sequence, pending local input, and handoff state. Reconnect reconciles authoritative server state before enabling controls.
- **Codex / ACP:** Codex remote connections/control and ACP sessions can expose remote-backed work, but lease and replay semantics are product responsibilities.
- **Fallback:** On uncertain reconciliation, reopen read-only and require explicit takeover; never resend buffered approvals automatically.
- **Acceptance:** A mobile/desktop handoff cannot duplicate Send, Interrupt, or Approve, and losing the controller does not imply the task stopped.

## 18. Sources, citations, generated artifacts, and exports

### 161 — Sources distinguish discovery, use, citation, and authority

**Priority:** P0 · **Owner:** Client-owned evidence model

- **Behavior:** A source row indicates whether it was suggested, searched, opened, read, quoted, cited, downloaded, or merely linked by another source. Show publisher/domain, content type, retrieval method, and agent/tool responsible.
- **Codex / ACP:** Codex task sidebars and tool items can expose sources; ACP tool content/resource links can carry them but do not define evidentiary status.
- **Fallback:** Unstructured CLI URLs are labeled `Observed in transcript` until an adapter confirms use.
- **Acceptance:** A link mentioned by the model cannot receive the same visual weight as a document actually fetched and used.

### 162 — Every external source shows freshness and refresh state

**Priority:** P0 · **Owner:** Client-owned evidence model

- **Behavior:** Show fetched-at time, source publish/update date when known, cache/live status, content fingerprint, and whether a newer retrieval exists. `Refresh` creates a new evidence version rather than mutating history.
- **Codex / ACP:** Web/MCP tools may expose metadata; ACP resource/tool content can transport it. The client owns freshness presentation.
- **Fallback:** If dates are unavailable, say `Date not reported`; do not substitute transcript time as publication time.
- **Acceptance:** Reopening a month-old task makes stale current-information claims visibly stale without invalidating timeless local sources.

### 163 — Citations deep-link to the exact supporting location

**Priority:** P0 · **Owner:** Client-owned navigation

- **Behavior:** Clicking a citation opens the relevant page anchor, PDF page, file line/symbol, artifact sheet/slide, transcript item, or captured excerpt and highlights the supported span when licensing and source format permit.
- **Codex / ACP:** ACP file locations/resources and Codex source/file metadata provide anchors; the viewer owns rendering.
- **Fallback:** Open the nearest stable container and show the captured excerpt plus `Exact location unavailable`.
- **Acceptance:** Citation navigation never dumps the user at an unrelated document start while pretending the exact claim is selected.

### 164 — Canonical source identity preserves versions instead of duplicating rows

**Priority:** P1 · **Owner:** Client-owned evidence store

- **Behavior:** Normalize redirects, tracking parameters, local path case, file aliases, and known repository links while retaining original URLs/paths. Group identical content hashes and expose materially changed versions.
- **Codex / ACP:** Source ids vary by runtime/tool; Integrator provides a cross-runtime identity layer.
- **Fallback:** When canonicalization confidence is low, keep separate rows with a possible-duplicate suggestion.
- **Acceptance:** The same document opened through three tools appears as one source with three provenance events, while changed content remains a new version.

### 165 — Artifact cards expose a real lifecycle

**Priority:** P0 · **Owner:** Client-owned artifact model

- **Behavior:** Use queued, generating, preview available, finalizing, ready, stale, superseded, failed, cancelled, and missing states. Show producing turn/tool, format, size, validation, save location, and whether the file is durable.
- **Codex / ACP:** Codex artifact viewer/tool items and ACP content/resource links can identify outputs, but the lifecycle is normalized client state.
- **Fallback:** Unstructured file mentions remain ordinary file links until existence and ownership are verified.
- **Acceptance:** A partial file cannot be labeled `Ready`, and closing the task cannot lose an artifact the UI called durable.

### 166 — The viewer opens the exact artifact version the transcript references

**Priority:** P0 · **Owner:** Client-owned versioning

- **Behavior:** Bind artifact links to immutable hash/version and producing turn. If the path now contains newer bytes, show both `Referenced version` and `Current file` with a comparison choice.
- **Codex / ACP:** Tool ids/turn ids and resource links provide lineage; Integrator hashes or snapshots outputs where policy permits.
- **Fallback:** If snapshots are forbidden, show captured metadata and a strong `File changed since this message` warning.
- **Acceptance:** Regenerating `report.pdf` never rewrites what an earlier transcript card appears to preview.

### 167 — Large artifact previews load progressively and remain cancellable

**Priority:** P1 · **Owner:** Client-owned viewer performance

- **Behavior:** Render metadata and the first useful page/sheet/slide/section quickly, show indexing/render progress, virtualize content, cap memory, and allow cancel/retry/open externally/download without blocking the transcript.
- **Codex / ACP:** Protocols may provide file/resource references; preview generation is client-owned.
- **Fallback:** Unsupported or oversized formats show a safe metadata card and external-open/export path.
- **Acceptance:** A multi-gigabyte log, workbook, or PDF cannot freeze navigation or exhaust the renderer while its preview is being prepared.

### 168 — Regeneration creates a version and a comparison, not silent replacement

**Priority:** P0 · **Owner:** Client-owned artifact versioning

- **Behavior:** Regenerate/convert/edit outputs as new versions with parent lineage, change summary, validation result, and Keep both/Promote/Revert controls. Preserve comments against their source version.
- **Codex / ACP:** New turns/tools generate new evidence; no protocol should imply path overwrite equals version history.
- **Fallback:** If the external tool overwrites in place, snapshot beforehand when allowed or warn that comparison/revert is unavailable.
- **Acceptance:** Users can identify which version was shared/exported and cannot accidentally approve comments against different bytes.

### 169 — Export packages are deterministic and self-describing

**Priority:** P0 · **Owner:** Client-owned export

- **Behavior:** Export selected task state, artifacts, sources, diffs, plans, and diagnostics with a manifest containing schema version, timestamps, hashes, provenance, omissions, redactions, and compatibility notes. Stable inputs produce stable ordering/names.
- **Codex / ACP:** Integrator synthesizes normalized state from native primitives; neither protocol defines this package.
- **Fallback:** If source redistribution is restricted, export citations/metadata and omission reasons rather than cached content.
- **Acceptance:** Re-import verifies hashes, explains unsupported fields before mutation, and never includes secrets or hidden reasoning by default.

### 170 — Broken artifact/source references degrade visibly and repairably

**Priority:** P0 · **Owner:** Client-owned reference integrity

- **Behavior:** When a file moves, source expires, permission is revoked, cache is cleared, or remote artifact disappears, keep the historical card and mark the broken edge. Offer locate, reauthorize, refetch, regenerate, or detach according to provenance.
- **Codex / ACP:** Runtime file/resource failures provide current evidence; Integrator preserves historical identity.
- **Fallback:** Never remove the reference solely because the target is unavailable.
- **Acceptance:** A cleanup operation previews affected references, and a missing target cannot make an earlier claim look as though it never cited or produced anything.

## 19. Collaboration, attention, notifications, devices, and account boundaries

### 171 — “Unread” requires meaningful visibility, not merely opening a task

**Priority:** P0 · **Owner:** Client-owned attention state

- **Behavior:** Mark new output read only after the relevant window is focused and the new region is visible or deliberately jumped to. Track last-read event per user/device while syncing a monotonic shared read position where appropriate.
- **Codex / ACP:** Thread/item updates provide event identity; read semantics are client/account state, not protocol completion.
- **Fallback:** If cross-device sync is unavailable, show local-only read state and never erase another device's attention marker.
- **Acceptance:** Background updates do not become read because a minimized window held the task open, and reconnect cannot move the read marker backward.

### 172 — Notification policy is event-specific, testable, and focus-aware

**Priority:** P0 · **Owner:** Client-owned notifications

- **Behavior:** Configure response ready, approval needed, question, failure, schedule result, remote disconnect, usage threshold, and update separately; choose banner, sound, badge, OS notification, quiet hours, and focused-window suppression. Include a test action.
- **Codex / ACP:** Codex/TUI notification settings and normalized lifecycle events supply triggers. ACP updates/permissions/stop reasons supply event data but not OS policy.
- **Fallback:** Unsupported OS notification channels remain disabled with explanation rather than silently dropping events.
- **Acceptance:** Testing never creates a fake unread task, and a blocking approval can override ordinary response-ready suppression only when policy says so.

### 173 — Notifications group by task and outcome and contain a safe next action

**Priority:** P1 · **Owner:** Client-owned notifications

- **Behavior:** Replace repetitive progress notifications with one updating group. Final notifications name project/task/runtime and outcome, avoid sensitive prompt/output text by default, and deep-link to the blocking or completed item.
- **Codex / ACP:** Stable thread/session ids and item/status events anchor grouping.
- **Fallback:** Platforms without updateable notifications receive rate-limited milestone notifications and a badge.
- **Acceptance:** Fifty tool events produce at most one progress notification group; clicking it opens the correct task without executing Approve, Retry, or Send.

### 174 — Approval notifications expire when their underlying request changes

**Priority:** P0 · **Owner:** Client-owned permission lifecycle

- **Behavior:** Attach notification actions to request id, task, runtime, control owner, and state version. Dismiss/expire them on response, cancellation, timeout, supersession, task takeover, or policy change.
- **Codex / ACP:** Both Codex and ACP approvals have request/response lifecycles; client notifications must honor them.
- **Fallback:** If OS action callbacks cannot be proven current, clicking only opens the task for review.
- **Acceptance:** An old notification can never approve a newer command, different host, changed network destination, or already-cancelled request.

### 175 — The attention queue prioritizes blockers without hiding chronology

**Priority:** P0 · **Owner:** Client-owned attention model

- **Behavior:** Present blocking approvals/questions, failures, completed results, warnings, and ordinary unread output with type, age, project, runtime, and owner filters. Rank by urgency while retaining stable chronological inspection and snooze.
- **Codex / ACP:** Normalize Codex server requests/status and ACP permission/prompt/tool/stop states.
- **Fallback:** Unstructured adapters contribute conservative `Needs review` items rather than guessing urgency.
- **Acceptance:** A new response-ready event cannot push an older destructive approval offscreen without an aggregate count or filter indication.

### 176 — Presence and control ownership are not the same badge

**Priority:** P0 · **Owner:** Client-owned collaboration

- **Behavior:** Show who is viewing, who is composing/commenting when supported, who controls the live task/browser/terminal, and who last changed shared settings. Presence expires quickly; control uses an explicit lease.
- **Codex / ACP:** Native identities/events may help, but neither protocol provides a complete collaborative-presence standard.
- **Fallback:** On single-user/local sessions show device/window ownership only; never invent remote collaborators.
- **Acceptance:** Closing a viewer clears presence without releasing another user's control, and a stale presence indicator cannot persist indefinitely after disconnect.

### 177 — Handoff is an atomic snapshot with acknowledgment

**Priority:** P0 · **Owner:** Client-owned collaboration

- **Behavior:** Capture task/session ids, control sequence, goal, runtime/config, permissions, plan, changed files, checkout state, active tools, pending approvals/questions, artifacts, verification, and known gaps at one timestamp. Recipient acknowledges before control transfers.
- **Codex / ACP:** Build from Codex thread/goal/items/status or ACP session/config/plan/tool state plus Integrator evidence.
- **Fallback:** If a live transfer is unsupported, create a read-only handoff package and require the recipient to resume/fork explicitly.
- **Acceptance:** State changes during snapshot either appear before its sequence boundary or in a clearly separate delta; none are silently lost between owners.

### 178 — Devices and remote sessions are reviewable and revocable

**Priority:** P0 · **Owner:** Client-owned account security

- **Behavior:** List signed-in devices/hosts, local runtimes, remote connections, active control leases, credential type, first/last seen, approximate region where appropriate, and revoke/sign-out actions. Require reauthentication for high-impact revocation.
- **Codex / ACP:** Codex remote/mobile/account surfaces may expose parts; ACP `logout` affects an agent connection but is not a full account-device registry.
- **Fallback:** Deep-link to vendor security settings when Integrator cannot revoke a vendor session, and invalidate its own local tokens/leases immediately.
- **Acceptance:** Revocation ends new control attempts, marks affected tasks, and never prints or copies session credentials.

### 179 — Compact/mobile review never hides approval-critical context

**Priority:** P0 · **Owner:** Client-owned responsive safety

- **Behavior:** On narrow screens, approval and review sheets still show operation, target path/origin/host, scope, diff/command summary, risk, duration, owner, and alternatives before the action buttons. Secondary evidence may collapse but remains one tap away.
- **Codex / ACP:** Structured approval/tool fields provide the context; responsive composition is client-owned.
- **Fallback:** If essential content cannot fit or render, allow Open on desktop/Copy details/Reject, but not blind approval.
- **Acceptance:** No breakpoint replaces a reviewed `Allow once` decision with an unlabeled icon, swipe gesture, or context-free notification action.

### 180 — Account/workspace switching preserves drafts and quarantines scoped state

**Priority:** P0 · **Owner:** Client-owned identity boundary

- **Behavior:** Before switching, show affected runtimes/tasks/automations/plugins/policies, preserve unsent drafts locally under the old identity, detach credential-scoped connections, and rebuild capability/policy state for the new workspace.
- **Codex / ACP:** Codex account/workspace auth and ACP authenticate/logout provide connection boundaries; client caches and drafts must be partitioned.
- **Fallback:** Require app/runtime restart when hot switching cannot prevent state leakage.
- **Acceptance:** A new workspace cannot see the prior workspace's private tasks, sources, plugins, MCP resources, usage, or draft attachments through cache or search.

## 20. Performance, storage, crash recovery, privacy, and audit integrity

### 181 — Blocking interaction events outrank bulk output

**Priority:** P0 · **Owner:** Client-owned event scheduler

- **Behavior:** Prioritize permission/question requests, cancellation acknowledgments, control-lease changes, fatal errors, and user input over token deltas, logs, source indexing, previews, and cosmetic animation. Maintain order within each causal stream.
- **Codex / ACP:** Structured request ids and session/turn/tool events enable prioritization; the renderer/event bus implements it.
- **Fallback:** Under overload, pause/coalesce low-priority rendering and preserve raw events for later replay.
- **Acceptance:** A million-line command cannot delay an approval card, Stop response, or typed composer character beyond the interactive budget.

### 182 — Backpressure coalesces replaceable state but never loses transitions

**Priority:** P0 · **Owner:** Client-owned event processing

- **Behavior:** Coalesce latest token text chunk, progress percentage, usage, plan full-list update, terminal viewport repaint, and status heartbeat where semantics allow. Preserve started/completed/failed, approval, file mutation, and audit transitions exactly once.
- **Codex / ACP:** ACP plan updates replace the full plan and tool updates patch by id; Codex structured notifications identify event types.
- **Fallback:** Unknown extension events remain ordered and bounded; they are not coalesced into security/core state.
- **Acceptance:** Stress fixtures end in the same normalized state with and without renderer throttling, with no missing lifecycle boundary.

### 183 — Search and indexing are incremental, cancellable, and scope-visible

**Priority:** P1 · **Owner:** Client-owned search infrastructure

- **Behavior:** Show indexed scopes, exclusions, freshness, progress, and result provenance. Typing a new query cancels obsolete work; opening a result never waits for full reindex. Respect project/account/privacy boundaries.
- **Codex / ACP:** Codex thread list/search and filesystem methods can supply data; local cross-runtime indexing remains client-owned.
- **Fallback:** Fall back to native runtime search or direct `rg`/metadata search with a visible reduced-scope label.
- **Acceptance:** A large workspace can be searched while indexing continues, and excluded secrets/binary/cache directories never appear in snippets.

### 184 — Unbounded logs spill safely while keeping a useful live tail

**Priority:** P0 · **Owner:** Client-owned terminal/log storage

- **Behavior:** Keep a bounded in-memory tail, stream older bytes to a task-scoped file with rotation/compression policy, expose truncation and total-byte counters, and support search/export without loading the entire log.
- **Codex / ACP:** Codex command output deltas and ACP terminal `outputByteLimit`/`truncated` make loss detectable.
- **Fallback:** When durable spill is unavailable, drop oldest chunks only after recording exact omitted byte/line estimates and a warning.
- **Acceptance:** Sustained gigabyte output does not crash the renderer, hide the latest error, or claim the transcript is complete.

### 185 — Cached blobs are content-addressed and reference-counted

**Priority:** P1 · **Owner:** Client-owned storage

- **Behavior:** Deduplicate identical screenshots, attachments, source snapshots, tool outputs, and artifact versions by cryptographic hash while retaining per-task provenance and access policy. Delete bytes only after all authorized references expire.
- **Codex / ACP:** Native ids provide provenance; Integrator owns cache identity and lifecycle.
- **Fallback:** If encryption/security domains differ, keep separate physical copies even when hashes match.
- **Acceptance:** Deduplication cannot let one account/project infer or open another scope's blob, and clearing one task does not break a still-referenced artifact.

### 186 — Disk pressure is surfaced before writes fail

**Priority:** P0 · **Owner:** Client-owned storage health

- **Behavior:** Monitor relevant volumes and classify space used by runtimes, transcripts, logs, repositories/worktrees, browser profiles, indexes, previews, downloads, and caches. Offer cleanup previews with size, age, rebuildability, and reference impact.
- **Codex / ACP:** No protocol owns host storage; runtime failures and artifact paths add context.
- **Fallback:** If category measurement is expensive, show verified volume free space and the largest known Integrator categories without guessing totals.
- **Acceptance:** Cleanup never deletes repositories, unsaved drafts, active task state, credentials, or irreplaceable artifacts under a generic `cache` label.

### 187 — Retention changes preview exactly what will disappear

**Priority:** P0 · **Owner:** Client-owned privacy/lifecycle

- **Behavior:** Retention rules distinguish transcript metadata, prompt/content, tool output, logs, browser data, sources, artifacts, diagnostics, audit, and vendor-native history. Show oldest/newest affected, bytes, active exemptions, remote copies, and broken references.
- **Codex / ACP:** Native archive/delete semantics differ; ACP session delete only guarantees removal from future lists, so claims must be qualified.
- **Fallback:** Where remote hard deletion is unverified, say `Removed from Integrator` and link/show vendor deletion status separately.
- **Acceptance:** A dry-run and post-delete receipt agree, and no UI says `Deleted everywhere` without evidence from every owning store.

### 188 — Repeated startup failure enters a useful safe mode

**Priority:** P0 · **Owner:** Client-owned crash recovery

- **Behavior:** After a crash loop, start with extensions/hooks/plugins/MCP auto-start, browser restore, remote reconnect, and active-task resume selectively disabled. Show the last crash phase and let the user re-enable components one group at a time.
- **Codex / ACP:** Integrator supervises runtimes and stores probe/crash evidence; protocols only participate after initialization.
- **Fallback:** A command-line safe-mode flag and recovery instructions remain available if the normal shell cannot render.
- **Acceptance:** One bad plugin, corrupt tab, or crashing runtime cannot make the whole app permanently unopenable or force deletion of user data.

### 189 — State database migrations are atomic, backed up, and observable

**Priority:** P0 · **Owner:** Client-owned persistence

- **Behavior:** Before schema migration, verify disk space and integrity, create a bounded recoverable backup, show progress for long work, journal completion, and roll back or open read-only recovery after interruption.
- **Codex / ACP:** This concerns Integrator's normalized/draft/view/audit stores, not native session databases it does not own.
- **Fallback:** If downgrade is unsupported, export a recovery package before migration and state the one-way boundary.
- **Acceptance:** Power loss at every migration checkpoint yields either the prior valid schema or the complete new schema, never silently reset history.

### 190 — Audit history is bounded, redacted, and tamper-evident

**Priority:** P0 · **Owner:** Client-owned security/audit

- **Behavior:** Record security-relevant config, trust, permission, control, auth, extension, schedule, export, and deletion events with actor, scope, source, prior/new state references, and chained integrity evidence. Redact content/secrets and apply documented retention.
- **Codex / ACP:** Structured ids/config/tool events supply evidence; unknown `_meta` remains untrusted and cannot alter the audit chain.
- **Fallback:** On filesystems without secure local key storage, provide best-effort append-only integrity with an explicit limitation.
- **Acceptance:** Editing/removing an audit entry is detectable, while the log cannot reconstruct a token, cookie, raw secret environment value, or hidden reasoning.

## 21. Micro-polish, help, disclosure, and interaction grammar

### 191 — Tooltips wait, work from the keyboard, and get out of the way

**Priority:** P1 · **Owner:** Client-owned design system

- **Behavior:** Use a consistent initial delay, shorter skip delay between adjacent controls, immediate close when appropriate, hover and focus access, screen-edge collision handling, and no tooltip for already-visible labels. Suppress the tooltip while its trigger opens a menu/popover.
- **Codex / ACP:** No protocol primitive. OpenCode and OpenHands provide source-level precedents for delay, nested-overlay suppression, focus, flip, shift, and auto-update.
- **Fallback:** Touch exposes equivalent help through long-press or an explicit info action, never hover-only knowledge.
- **Acceptance:** A tooltip neither covers the menu it describes nor reopens under the pointer immediately after the user clicks its trigger.

### 192 — Hover actions never shift content or vanish during acquisition

**Priority:** P1 · **Owner:** Client-owned design system

- **Behavior:** Reserve geometry for row actions or overlay them without moving text. Keep actions visible while the pointer travels from row to button and while keyboard focus remains inside; selected/focused state cannot depend on hover.
- **Codex / ACP:** Native item state supplies meaning; layout is client-owned.
- **Fallback:** Compact/touch rows expose a persistent overflow button.
- **Acceptance:** Moving toward Rename/Archive/Copy/Retry cannot cause the target to slide away, collapse, or activate a neighboring row.

### 193 — Escape follows one predictable dismissal ladder

**Priority:** P0 · **Owner:** Client-owned input grammar

- **Behavior:** Escape first cancels IME/completion, then closes tooltip/popover/menu, then exits inline edit/selection/annotation, then closes non-destructive drawer/dialog, then clears transient mode. It never interrupts a task or discards a draft without a separately bound/confirmed action.
- **Codex / ACP:** Interrupt/cancel primitives remain explicit controls; the key ladder is client-owned.
- **Fallback:** Platform-native modal behavior wins where required, but is documented and tested.
- **Acceptance:** Repeated Escape unwinds exactly one visible layer at a time with focus restoration and no hidden state left armed.

### 194 — Floating surfaces stay inside the usable screen at every zoom

**Priority:** P1 · **Owner:** Client-owned geometry

- **Behavior:** Menus, tooltips, context menus, completion lists, approval sheets, and color/setting pickers flip, shift, resize, or scroll around screen edges, title bars, notches, taskbars, keyboards, and pane boundaries. Anchor to logical controls during layout change.
- **Codex / ACP:** No protocol primitive.
- **Fallback:** If the anchor disappears, close and restore focus instead of leaving an orphan overlay.
- **Acceptance:** Automated geometry tests cover 100–200% zoom, all window corners, narrow panes, multi-monitor scale differences, and on-screen keyboard appearance.

### 195 — Inline rename has explicit commit, cancel, and conflict rules

**Priority:** P1 · **Owner:** Client-owned editing grammar

- **Behavior:** Enter commits when valid, Escape restores the exact original, blur commits only when that surface's convention is unambiguous, and navigation prompts or cancels predictably. Select the editable stem where useful; preserve extensions/required syntax.
- **Codex / ACP:** Codex thread naming and filesystem operations provide mutations; the field lifecycle is client-owned.
- **Fallback:** On remote conflict, keep the user's draft and present current/server values with retry rather than overwriting.
- **Acceptance:** Double submission, empty forbidden names, case-only rename, duplicate name, latency, and concurrent rename each have deterministic outcomes.

### 196 — Relative times always reveal the exact timestamp and timezone

**Priority:** P1 · **Owner:** Client-owned formatting

- **Behavior:** Use calm relative labels where scannable, update at sensible intervals, and expose exact localized date/time, timezone/offset, and source timestamp on hover/focus/details. Scheduled events additionally show target timezone.
- **Codex / ACP:** Protocol timestamps may have different clocks; Integrator records source and receipt time where needed.
- **Fallback:** Clock-skewed or missing timestamps are labeled, not normalized into false precision.
- **Acceptance:** `2h ago`, run history, audit, usage reset, and schedule next-run can all be reconciled to exact instants across DST and devices.

### 197 — Badges use stable thresholds and fixed geometry

**Priority:** P1 · **Owner:** Client-owned design system

- **Behavior:** Define zero/hidden, single-digit, capped count, dot-only, warning, and unknown states per badge. Reserve width or use tabular numerals; animate only meaningful state transitions and honor reduced motion.
- **Codex / ACP:** Counts derive from normalized unread/approval/error/tool state; visuals are client-owned.
- **Fallback:** If count fidelity is approximate, use a dot or `99+`, not a precise-looking number.
- **Acceptance:** Rapid counts do not jitter the sidebar, and color is never the only distinction between unread, blocked, failed, and running.

### 198 — Empty states explain scope and offer one relevant action

**Priority:** P1 · **Owner:** Client-owned content design

- **Behavior:** Differentiate truly empty, filtered empty, not loaded, unavailable capability, permission denied, offline, and error. State the current scope and provide the smallest relevant action such as Clear filter, Connect runtime, Open project, Retry, or Learn why.
- **Codex / ACP:** Capability/session/tool state determines the condition; the client writes and places the empty state.
- **Fallback:** Unknown state is `Not available yet` with diagnostics, never a cheerful `Nothing here`.
- **Acceptance:** Search results with an active filter cannot look like lost history, and an unsupported feature cannot look like a temporary empty list.

### 199 — Retry is operation-specific and idempotence-aware

**Priority:** P0 · **Owner:** Adapter-derived error recovery

- **Behavior:** Name what will retry—probe, reconnect, fetch, upload, tool call, prompt, clone, install, save, or render—and whether prior execution may have succeeded. Reuse idempotency keys or reconcile state before repeating external writes.
- **Codex / ACP:** Request/tool/session ids and lifecycle states support reconciliation; the adapter knows which operations are safe to replay.
- **Fallback:** When outcome is uncertain, offer Check status and Copy details before Retry anyway.
- **Acceptance:** A timeout after send/publish/purchase/deploy cannot surface an innocent generic Retry button that may duplicate the external effect.

### 200 — “What changed?” connects product updates to actual capability changes

**Priority:** P1 · **Owner:** Client-owned release/migration UI

- **Behavior:** After app, adapter, runtime, protocol, skill, or plugin update, summarize user-visible additions, removals, migrations, policy changes, new authority, and known degradation relevant to installed components. Link directly to affected settings/features and persist dismissal per version.
- **Codex / ACP:** Runtime capabilities and versions provide observed deltas; Codex changelog/docs and ACP versions provide source context. Integrator owns the personalized comparison.
- **Fallback:** If release metadata is missing, show only measured capability/schema differences and label the vendor explanation unavailable.
- **Acceptance:** A feature disappearing due to a downgraded CLI or revoked policy is not celebrated as a release note, and changed permissions/hooks require review rather than passive dismissal.

## 22. Implementation and test discipline

### 22.1 P0 ordering

Implement the P0 items in this dependency order:

1. Stable task/project/checkout identity and durable local state.
2. Capability negotiation and adapter state machines.
3. Composer/draft/queue and truthful lifecycle control.
4. Transcript grouping/virtualization/scroll.
5. Permission, files, terminal, diff, and Git safety.
6. Recovery/auth/attention.
7. Extension/config/browser/schedule/source provenance.
8. Multi-window, remote-control, notification, and account boundaries.
9. Storage, recovery, privacy, audit, keyboard, accessibility, and platform fallback.
10. Usage, diagnostics, migration, and release compatibility.

P1 polish should not delay P0 truth, but the geometry/state APIs must leave room for it.

### 22.2 Required test lanes

Every item gets at least one test in the lane implied by its acceptance check:

- unit state-machine test;
- adapter contract fixture for Codex and ACP;
- degraded PTY/no-capability fixture;
- integration test with restart/reconnect where relevant;
- keyboard/screen-reader test;
- visual test across light/dark/high-contrast and Windows/macOS geometry;
- stress test for streaming/history/concurrency;
- secret/redaction test for any copied, indexed, logged, or exported data.

### 22.3 Capability truth table

For each runtime version, generate a matrix with:

```text
QOL item
Native primitive
Negotiated capability
Integrator-owned state
Fallback
Known loss of fidelity
Test fixture
```

Do not mark an item “supported” merely because the control renders. It is supported only when native state, UI state, persistence, cancellation/recovery, and fallback have been tested together.
